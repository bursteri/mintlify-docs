---
title: "Meta event_id deduplication"
description: "Use one stable event_id across browser Pixel and server CAPI events while keeping PlainRouter retries idempotent and observable."
---

`event_id` solves two related but distinct duplicate problems:

1. PlainRouter treats a repeated event ID as an idempotent API retry.
2. Meta uses the matching browser `eventID` and server `event_id` to recognize two copies of the same logical event.

The safest design assigns the ID once at the business-event boundary and preserves it through every retry and delivery path.

## Choose a stable ID

Use an identifier that is:

- Stable for one logical event.
- Different for separate events in the same order lifecycle.
- Free of email addresses, phone numbers, names, and other personal data.
- No more than 128 characters for the PlainRouter API.

Examples:

```text
purchase:ORDER-1042
refund:REFUND-2088
lead:01K2EXAMPLE7SRY4RY3J2P5M8T
```

Do not generate a new UUID inside each retry attempt. Generate or derive the ID before enqueueing the event, then store it with the job or order record.

## Understand PlainRouter API idempotency

Send the stable value in the JSON body:

```json
{
  "event_id": "purchase:ORDER-1042",
  "event_name": "Purchase",
  "consent_basis": "consent",
  "consent": {
    "ad_storage": "granted",
    "ad_user_data": "granted",
    "ad_personalization": "granted",
    "source": "checkout_cmp"
  },
  "value_data": {
    "value": "49.90",
    "currency": "EUR",
    "order_id": "ORDER-1042"
  }
}
```

The first accepted request returns HTTP `202` with `duplicate: false`. A retry with the same ID returns HTTP `200` with `duplicate: true` and the same canonical event ID.

You can send an `Idempotency-Key` header instead. If both the header and body field are present, their values must match or PlainRouter returns validation error `422`.

## Pair browser Pixel and server CAPI events

Meta's browser option is named `eventID`, while the server field is named `event_id`. Use the same value and the same logical event name on both paths:

```js
const eventId = "purchase:ORDER-1042";

fbq(
  "track",
  "Purchase",
  { value: 49.90, currency: "EUR" },
  { eventID: eventId }
);
```

```ts
import {
  configurePlainrouter,
  createEvent,
} from "@plainrouter/sdk";

const signalSecret = process.env.PLAINROUTER_SIGNAL_SECRET;
if (!signalSecret) throw new Error("PLAINROUTER_SIGNAL_SECRET is required");

configurePlainrouter({ signalTrackerSecret: signalSecret });

await createEvent({
  body: {
    event_id: "purchase:ORDER-1042",
    event_name: "Purchase",
    consent_basis: "consent",
    consent: {
      ad_storage: "granted",
      ad_user_data: "granted",
      ad_personalization: "granted",
      source: "checkout_cmp",
    },
    value_data: {
      value: "49.90",
      currency: "EUR",
      order_id: "ORDER-1042",
    },
  },
});
```

This manual pairing is useful when you own both paths. Do not run it in addition to PlainRouter's managed Pixel for the same event.

## Let PlainRouter manage the pair

When you [connect Meta](/signals/connect-meta) and track through `signalq`, PlainRouter generates one event ID, sends it as the Meta Pixel `eventID`, and carries the same value through the collector to the server delivery.

```js
const eventId = await signalq("track", "Purchase", {
  value: "49.90",
  currency: "EUR",
  order_id: "ORDER-1042"
});
```

This path avoids maintaining a second browser/server coordination channel. Remove another Pixel or CAPI sender for the same dataset after validating the managed destination.

## Avoid common deduplication failures

| Failure | Result | Fix |
| --- | --- | --- |
| A new ID is generated on each server retry. | PlainRouter and Meta see new events. | Persist one ID with the business event. |
| Browser and server use different IDs. | Meta cannot recognize the pair by ID. | Assign the ID before either path sends. |
| One order ID is reused for purchase and refund. | Different lifecycle events collide. | Prefix or otherwise distinguish the event type. |
| Two integrations send the same event with unrelated IDs. | Duplicate conversions can remain. | Keep one owner for the browser/server pair. |
| A `202` is treated as final Meta acceptance. | Delivery failures are hidden. | Read the event delivery trace after ingestion. |

## Verify the result

Retrieve the event by ID and inspect its delivery trace. `duplicate: true` proves a PlainRouter idempotent replay; it does not by itself prove that Meta deduplicated a browser/server pair.

For the managed browser flow, inspect the browser Pixel call and `/v1/events` request in developer tools. Both should carry the same ID. Then use Meta Test Events and PlainRouter's stored delivery state to verify the destination path.
