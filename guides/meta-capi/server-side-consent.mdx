title: "Server-side tracking consent"
description: "Model consent for server-side tracking, send truthful Meta CAPI permission states, and understand PlainRouter's fail-closed behavior."
---

Server-side transport does not remove the need for a lawful, product-specific consent decision. PlainRouter requires every public Conversion API event to declare `consent_basis` and rejects a consent-based event unless downstream advertising permissions are granted.

This guide explains PlainRouter's technical enforcement. It is not legal advice; your policy and consent design must reflect the jurisdictions and processing purposes that apply to you.

## Map the three permissions

PlainRouter's explicit consent snapshot uses three fields:

| Field | What it controls in this integration |
| --- | --- |
| `ad_storage` | Reading or writing browser storage such as `_fbp`, `_fbc`, and visitor state. |
| `ad_user_data` | Using customer and network data for downstream advertising delivery. |
| `ad_personalization` | Using the event for advertising personalization. |

Each field accepts `granted`, `denied`, or `unknown`. PlainRouter never turns a missing, unknown, or unrecognized value into a grant.

For a direct server request, `ad_user_data` and `ad_personalization` must be `granted` for `consent_basis: "consent"`. `ad_storage` must truthfully describe whether the flow used browser storage. Browser-originated collection requires all three grants.

## Send a complete consented event

Capture the decision time and name the system that supplied it:

```ts
import {
  configurePlainrouter,
  createEvent,
  type CreateEventData,
} from "@plainrouter/sdk";

type ConsentedBody = Extract<
  CreateEventData["body"],
  { consent_basis: "consent" }
>;

const signalSecret = process.env.PLAINROUTER_SIGNAL_SECRET;
if (!signalSecret) throw new Error("PLAINROUTER_SIGNAL_SECRET is required");

configurePlainrouter({ signalTrackerSecret: signalSecret });

const body: ConsentedBody = {
  event_id: "purchase:ORDER-1042",
  event_name: "Purchase",
  event_time: Math.floor(Date.now() / 1000),
  action_source: "website",
  consent_basis: "consent",
  consent: {
    ad_storage: "granted",
    ad_user_data: "granted",
    ad_personalization: "granted",
    captured_at: "2026-08-09T12:00:00Z",
    source: "checkout_cmp",
  },
  user_data: {
    email: "buyer@example.com",
  },
  click_ids: {
    fbp: "fb.1.1786271000000.1234567890",
  },
  value_data: {
    value: "49.90",
    currency: "EUR",
    order_id: "ORDER-1042",
  },
};

const result = await createEvent({ body });

if (result.error) {
  throw new Error(`Event rejected: ${JSON.stringify(result.error)}`);
}
```

This example includes `fbp`, so `ad_storage: "granted"` is the truthful state. For a server-only event that did not read or write browser storage, send the actual `ad_storage` state and omit browser identifiers.

## Fail closed before calling the API

Keep the application-side check close to the event builder:

```ts
type AdvertisingConsent = {
  adStorage: "granted" | "denied" | "unknown";
  adUserData: "granted" | "denied" | "unknown";
  adPersonalization: "granted" | "denied" | "unknown";
  capturedAt: Date;
  source: string;
};

export function canSendMetaCapi(consent: AdvertisingConsent): boolean {
  return consent.adUserData === "granted"
    && consent.adPersonalization === "granted";
}
```

If `canSendMetaCapi` is false, do not send a normal purchase through the public Conversion API. PlainRouter also enforces this boundary: contradictory or incomplete consent returns HTTP `422` and creates no event.

Do not change a denied purchase to `legitimate_interest` as a fallback. The public contract restricts legitimate-interest requests to modeled lifecycle operations; authenticated server-revenue adapters are separate product paths.

## Use one consent adapter consistently

The API accepts:

- `consent` for PlainRouter's explicit three-permission snapshot.
- `consent_mode` for Google Consent Mode v2 fields.
- `tcf` for a supported TCF v2 string and optional capture time.

You may send more than one adapter only when their normalized permission states agree. Conflicting adapters return validation error `422`.

Prefer the adapter that is closest to your actual consent source. Do not translate a denial into an absent field or an `unknown` value to make the request pass.

## Handle changes and withdrawal

For browser collection, send every state change through `signalq("consent", ...)`. An explicit withdrawal stops consent-dependent transmission, clears PlainRouter-owned browser identifiers, and sends the bounded withdrawal receipt when the flow was previously transmitting.

For your server application:

1. Update the consent state in the authoritative customer or session record.
2. Stop enqueueing future advertising events when downstream grants are absent.
3. Ensure queued jobs re-read the current decision when your policy requires it.
4. Use the [user-data deletion operation](/reference/conversion-api#delete-retained-user-data) for a verified deletion request; withdrawal alone is not a retroactive deletion command.

## Keep data categories aligned

- Put normalized customer identifiers under `user_data`.
- Put `fbp` and `fbc` under `click_ids` and keep them unhashed.
- Put price, currency, order ID, contents, and item count under `value_data`.
- Keep the Signals workspace secret on the server.
- Never put identity values or secrets in URLs, prompts, or logs.

For identifier behavior, see [`fbp` and `fbc` explained](/guides/meta-capi/fbp-fbc). For browser consent transitions, see [Track events and consent](/signals/track-events).
