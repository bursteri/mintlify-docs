Use Plainrouter's [Model Context Protocol (MCP)](https://modelcontextprotocol.io/introduction) server to inspect workspace Signals setup, compare arrivals, read an authorized Meta ad account, and request creative changes for human approval. Start with synthetic data or connect your workspace.

## What can I do with Plainrouter MCP?

| Task | Start with | Result |
| --- | --- | --- |
| Inspect Signals setup | `get_install_instructions` | Managed-hostname DNS and snippet material, plus stored first-arrival state. |
| Compare arrivals and clicks | `get_arrivals_comparison` | Stored workspace counts for a 7, 30, or 90 day window. |
| Confirm account access | `get_account_state` | The authorized workspace, selected Meta ad account, connection, and available capabilities. |
| Diagnose conversion signals | `get_signal_health` | Stored collection, delivery, matching, and reconciliation diagnostics. |
| Inspect stored performance | `get_performance` | An account-scoped comparison of gateway and Meta conversions. |
| Track an action proposal | `list_actions`, `get_action_batch`, `get_action`, `get_action_decision_receipt`, `get_action_policy` | Stored outcomes, receipts, and current policy; requires a Write key even though these are reads. |
| Review creatives | `get-creative-library` | Account images and videos with associated ads and recent performance history. |
| Request a creative change | `upload-asset` or `duplicate-ad-with-creative` | A governed proposal for review; a supported ad copy is created paused only after the execution gates pass. |

The legacy `adjust_budget` and `set_status` MCP proposals do not execute budget or delivery-status changes. **Suggest only** records proposals and approvals without executing them.

For repeatable Signals tasks, the server also supplies three [built-in prompts](/mcp/tools#built-in-signals-prompts): installation, claimed-versus-counted comparison, and signal health. They return instructions; the client still needs authorization to run the referenced tools.

## How do I get started?

<Steps>
  <Step title="Connect a client">
    Use the sandbox without an account, or configure the production endpoint with a Workspace key. Follow [Setup](/mcp/setup).
  </Step>
  <Step title="Verify the account">
    For account-specific work, call `get_account_state` and confirm the returned workspace and Meta ad account. For workspace installation, call `get_install_instructions` and confirm its workspace; no Meta account is required.
  </Step>
  <Step title="Choose a workflow">
    Start with a read. Use [Signals diagnostics](/mcp/tools#get_signal_health), or follow the [creative proposal walkthrough](/actions/creative-workflow) when you are ready to request a change.
  </Step>
</Steps>

## Connection details

| Setting | Value |
| --- | --- |
| Production URL | `https://plainrouter.com/mcp` |
| Sandbox URL | `https://plainrouter.com/mcp/sandbox` |
| Transport | Streamable HTTP; each request is processed independently |
| Protocol | `2026-07-28` discovery; legacy `initialize` clients remain supported |
| Production credential | Workspace key sent as a bearer credential |
| Sandbox credential | None; all four sandbox tools return synthetic data |
| Account scope | One workspace per key; eligible account selected per account-scoped call. Older bound keys retain their account restriction. |

### Which clients can connect?

The [setup guide](/mcp/setup#configure-claude-code-for-your-meta-ad-account) includes Claude Code configuration. Other clients need remote HTTP MCP support and a way to send a fixed bearer credential. A client that requires OAuth sign-in for every remote server cannot use Plainrouter's production token flow as documented here.

Custom clients should follow the [protocol and header requirements](/mcp/setup#which-mcp-protocol-should-my-client-use). Plainrouter does not issue an `Mcp-Session-Id`; authenticate each production tool request with the workspace token.

## Access and approval

A workspace owner or member creates a key within their current role under **Settings → Workspace keys**. Start with the **Read** tier for account and creative-library inspection; proposal-producing tools and the [Actions read tools](/mcp/tools#read-actions-and-policy) require **Write**. [Choose a token tier](/mcp/workspace-tokens#access-tiers).

<Note>
  Plainrouter MCP uses Workspace keys. OAuth management credentials and Server secrets do not authenticate MCP tool calls.
</Note>

Reads, diagnostics, and proposals have different effects. `get_signal_health` reads stored measurements; `get-creative-library` contacts Meta. The optional `verify_signal_ingestion` diagnostic writes an identity-free event and does not prove a real website arrival. Creative proposal calls write to Plainrouter; they do not directly create the Meta ad.

Policy checks, human approval, and provider verification govern supported creative execution. A proposal or approval is not **Landed**. Review the [tool reference](/mcp/tools) for exact permissions and the [proposal review guide](/actions/review-proposals) for execution states.
