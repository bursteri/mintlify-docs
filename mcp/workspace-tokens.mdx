A **workspace key** authenticates Plainrouter MCP clients within one workspace. New keys created in **Settings → Workspace keys** are not pinned to one ad account. Account-scoped calls select an active account owned by that workspace. Older account-bound keys retain their original restriction.

The interface calls these credentials workspace keys; API fields and older integrations may still call them workspace execution tokens. They are separate from the Signals **Server secret** and **Management keys**. See [Authentication](/api/authentication#which-credential-should-i-use).

## Issue a token

Sign in as the workspace owner or a current team member and select the workspace your agent should use. Members can issue Read keys; Write keys also require update permission. The page lists and revokes only your own keys. A key can be created before connecting an ad account, but account reads need an eligible account and active provider connection.

1. Open **Settings → Workspace keys**.
2. Enter a **Name**, choose the **Read** or **Write** tier, and select a 30, 90, or 365 day expiry.
3. Choose **Create key**, then **Copy** the revealed key. It is shown once.
4. Configure your MCP client with `https://plainrouter.com/mcp` and the key as its bearer credential. The reveal dialog includes Claude Desktop and Claude Code configuration examples.
5. Call `get_account_state` and confirm the returned workspace and intended account before further work.

```http
Authorization: Bearer <workspace-key>
```

Store the key in your client's protected configuration or a secret manager. Keep it out of source control, logs, URLs, screenshots, and agent prompts.

For developer automation, the [management API](/api/authentication#how-do-i-use-the-management-api) provides the same role-capped issuance and revocation using a separate Management key. Revoking that Management key does not revoke workspace keys it issued.

## How does account selection work?

For tools that accept `account_id`, use Plainrouter's positive integer advertising-account ID, not Meta's external ad account ID. For example:

```json
{
  "account_id": 91
}
```

| Key and workspace state | Selection rule |
| --- | --- |
| New workspace key; one eligible active account | Account-scoped tools can select it when `account_id` is omitted. Confirm the returned account. |
| New workspace key; multiple eligible active accounts | Supply `account_id` for the intended account on each account-scoped call. |
| New workspace key; no eligible active account | Connect an account before using account-scoped tools. |
| Older key bound to an account | Omit `account_id` or supply that same bound ID. A different account is rejected. |

An eligible account for an unbound key must be owned by the key's workspace, active, and have an active provider connection. A destination binding to another workspace's account does not grant access. The key cannot switch workspaces or use an ownerless team account.

## Access tiers

| Tier | Workspace abilities | MCP access |
| --- | --- | --- |
| **Read** | `workspace:read` | Account, Signals and creative reads; the consent-safe ingestion diagnostic; legacy Launcher batch status where enabled. |
| **Write** | `workspace:read`, `workspace:write` | Read access plus governed action and creative proposals; legacy Launcher drafting and preview where enabled. |

New keys expose Read and Write, not Admin. Older Admin-tier credentials may still appear in compatibility responses; their tier does not bypass policy, human approval, provider verification, or account restrictions. A workspace key is not a management key or browser session.

Plainrouter rechecks the issuer's current workspace role and the linked grant on requests. An expired or revoked grant cannot authorize operations even when the key's own expiry has not passed. Feature enablement remains separate from key permissions: a key does not enable [legacy Launcher](/launcher/connect-drive).

## Workspace grants

Each execution credential is linked to a grant that identifies its principal, workspace, allowed operations, and expiry. Plainrouter checks that the grant is active and covers the requested operation, in addition to the credential's existing account and role restrictions.

Token-management responses include `grant_id`. An authorized administrator can use [`revoke_grant`](/mcp/tools#revoke_grant) to stop operations backed by that grant. A human delegator can also revoke their agent's grant. Revocation is scoped to the workspace and recorded as `grant.revoked`; it does not undo earlier provider actions.

### Inspect and revoke a grant in the dashboard

Sign in as the workspace owner and open **Workspace settings → Workspace grants**. Each grant shows its principal, tier, **Live**, **Expired**, or **Revoked** status, bound token name, and expiry. Expand **Exact operations** to inspect what it authorizes. Inspect the linked grant here; **Settings → Workspace keys** lists the key's status and last use.

1. Identify the intended principal and bound token before making a change.
2. For a live grant, click **Revoke**, then confirm **Revoke grant**.
3. Confirm the grant now shows **Revoked**. Expand its **Receipt** to inspect the audit entry, sequence, and hash prefix.

The receipt records authorization revocation; it is not a Meta execution receipt. Revocation prevents subsequent operations under the grant and does not reverse earlier advertising actions. Grants cannot be edited to add operations; issue a replacement credential when the authorized scope must change.

If no grants appear, confirm the workspace and whether a credential has been issued. If the section is unavailable, check that you are signed in as the owner. An expired or already revoked grant has no live-grant **Revoke** action. If confirmation fails, keep the error and recheck the grant's displayed status before assuming access has stopped.

## Rotate or revoke a token

Open **Settings → Workspace keys** to inspect names, creation time, last use, expiry, and **Active**, **Expired**, or **Revoked** status.

To replace a key, create a new one, install it in the client, and verify `get_account_state` with the intended account. Then use **Delete** on the old key and confirm. The current page does not have a Rotate button. If a key is exposed, delete it immediately before preparing its replacement.

Deleting a workspace key revokes its credential and grant; the revoked record remains security history. It does not undo earlier provider actions. Issuance and revocation record `token.issued` and `token.revoked` metadata without plaintext credentials.

## Troubleshoot

### The client receives `401 Unauthorized`

Check the complete bearer credential, expiry, revocation, grant state, and issuer's current role. Use a workspace key, not a Management key, OAuth management credential, or Signals Server secret. Older account-bound keys also depend on the bound account remaining available.

### The tool asks for an account or rejects the selected account

Supply `account_id` when the workspace has multiple eligible active accounts. Verify the account is owned by this workspace and its connection is active. Do not use Meta's external ID in this field. An older bound key cannot select another account; create a new workspace key when that restriction no longer fits the intended work.

### A tool reports insufficient permission

Use Read for reads and Write for proposal-producing tools. Create a replacement with the needed tier; do not try to elevate an existing key. Missing feature enablement or provider permissions is separate from its tier.

### You cannot open Workspace keys

Confirm you are the owner or a current member of the selected workspace's team. Write issuance requires update permission; you cannot list or delete another member's workspace keys from this page. **Management keys** is a different settings page and does not supply MCP execution credentials.
