Use the Actions API to preview and submit a governed proposal, then follow its stored outcome from your application. In **Ask**, a person approves every change first. In **Full**, the workspace lets changes run automatically without a per-change approval. Every change gets a receipt, and the kill switch stops all changes. The five read endpoints inspect Plainrouter records without calling Meta or changing ads. Proposal submission creates a Plainrouter batch; it does not execute a provider change during the request.

The Actions API covers a focused set of governed Meta changes, not the full Meta Marketing API. The [Meta Ads API guide](https://plainrouter.com/library/meta-ads-api) explains the difference.

## Before you start

- Create a **Write Workspace key** for the intended workspace, with an active grant covering `propose-actions`. This grant is required for Actions reads too; a normal Read key is insufficient. Older Admin keys still need the applicable grant and current role.
- Connect an active Meta ad account owned by that workspace. Confirm its scope with [`get_account_state`](/mcp/tools#get_account_state).
- Obtain the workspace's integer ID and Plainrouter's internal integer `account_id`. The latter is different from Meta's external account ID. The examples use workspace `42` and account `91`; replace both.
- Load the key into `PLAINROUTER_WORKSPACE_KEY` through your secret manager. A Signals Server secret, Management key, OAuth management credential, or browser session cannot replace it.

Use this base URL for all paths below:

```text
https://plainrouter.com/api/v1/agent/workspaces/{workspace}
```

Send `Authorization: Bearer <workspace-key>` and `Accept: application/json`. For POST requests, also send `Content-Type: application/json`.

### Select the account

Supply a positive integer `account_id` as a query parameter on GET requests and in the JSON body on POST. You may omit it when there is only one eligible active account. Multiple eligible accounts require an explicit selection. An older account-bound key accepts only its bound account. The workspace in the URL must match the key's workspace. See [account selection](/mcp/workspace-tokens#how-does-account-selection-work).

## Endpoints

| Method | Path relative to the base URL | Result |
| --- | --- | --- |
| `GET` | [`/actions`](/api/actions/actionreadapi/list-actions) | Paginated actions for the selected account. |
| `GET` | [`/action-batches/{actionBatch}`](/api/actions/actionreadapi/get-action-batch) | One batch and its actions. |
| `GET` | [`/actions/{action}`](/api/actions/actionreadapi/get-action) | One action. |
| `GET` | [`/actions/{action}/decision-receipt`](/api/actions/actionreadapi/get-decision-receipt) | Its stored decision receipt and audit-chain reference. |
| `GET` | [`/actions/policy`](/api/actions/actionreadapi/get-action-policy) | Current workspace policy, including effective defaults. |
| `POST` | [`/actions/dry-run`](/api/actions/actiondryrunapi/preview-actions) | Preview policy decisions and diffs without creating a proposal. May read provider state. |
| `POST` | [`/actions`](/api/actions/actionproposalapi/propose-actions) | Submit a proposal through the policy and approval workflow. |

`{actionBatch}` and `{action}` are the ULIDs returned by Plainrouter, not Meta object IDs. All successful reads return HTTP `200`.

## List and inspect actions

```bash
curl --fail-with-body --get \
  https://plainrouter.com/api/v1/agent/workspaces/42/actions \
  --header "Authorization: Bearer $PLAINROUTER_WORKSPACE_KEY" \
  --header 'Accept: application/json' \
  --data-urlencode 'account_id=91' \
  --data-urlencode 'status=pending' \
  --data-urlencode 'page=1'
```

The [list reference](/api/actions/actionreadapi/list-actions) defines the query and response fields. Filter by an exact [action status](/reference/statuses-and-terms#action-statuses), such as `pending`, `verified`, or `execution_uncertain`; batch-only values such as `completed` are invalid. Pages contain at most 25 actions, ordered by action ID descending. Continue through the returned pages; there is no configurable `per_page` parameter.

To inspect a returned action, request `/actions/{action}?account_id=91` and use the [single-action reference](/api/actions/actionreadapi/get-action). To inspect its batch, request `/action-batches/{actionBatch}?account_id=91` and use the [batch reference](/api/actions/actionreadapi/get-action-batch). Confirm the scope and read both batch and action statuses.

## Interpret current disposition and recovery

List, single-action, and batch reads include each action's current `disposition` alongside its historical `status` and `batch_status`. The [action response reference](/api/actions/actionreadapi/get-action) defines the fields. Use `receipt_status` for current execution-receipt state and `outcome_status` for later measurement; measurement is separate from execution verification. An unavailable reason, check time, or recovery value remains unknown, not successful.

Read `compensation_reason_code` with `recovery_disposition` using the [recovery interpretation](/actions/audit-log#interpret-unavailable-outcomes-and-recovery). `late_restored` records later compensation evidence without rewriting the earlier action or batch result. The [batch response reference](/api/actions/actionreadapi/get-action-batch) defines `restoration_summary`; `all_receipts_compensated_late` means every existing execution receipt in that batch is compensated and at least one has late-restoration evidence. It does not mean every proposed action executed, and it does not turn the batch into a successful original execution.

Keep nullable values as unknown. A historical `rollback_incomplete` can remain alongside later restoration evidence; read both rather than replacing one with the other.

## Read the current policy

```bash
curl --fail-with-body --get \
  https://plainrouter.com/api/v1/agent/workspaces/42/actions/policy \
  --header "Authorization: Bearer $PLAINROUTER_WORKSPACE_KEY" \
  --header 'Accept: application/json' \
  --data-urlencode 'account_id=91'
```

The [policy response reference](/api/actions/actionreadapi/get-action-policy) defines the current policy fields: `id`, `workspace_id`, `execution_mode`, `outcome_check_after_hours`, and `anomaly_threshold_percent`. If no policy has been saved, the read returns effective defaults with `id: null`; it does not create a policy. This is the **current** policy, not the frozen mode or policy evidence from an earlier proposal. Review [policy and safety](/actions/policies-and-safety) before interpreting execution permissions.

## Retrieve a decision receipt

Request `/actions/{action}/decision-receipt?account_id=91` with the same headers. The [decision-receipt reference](/api/actions/actionreadapi/get-decision-receipt) defines its response. The stored `document` records the terminal outcome and available verification evidence. `document_sha256` is a digest of the canonical document, not the downloaded JSON file's formatting; `chain_entry` identifies the receipt's audit event.

The stored `document`, digest, and chain reference remain immutable. The separate `disposition` can reflect later recovery; do not include it when checking `document_sha256`. A receipt may not exist yet, and a receipt can describe failure. Check its terminal status and verification evidence before reporting success. This endpoint exposes one scoped receipt, not the complete workspace audit export. See [receipt interpretation and integrity limits](/actions/audit-log#download-an-action-decision-receipt).

### What does `receipt_not_available` mean?

For a visible action without an execution receipt, the REST endpoint returns HTTP `404` with this error:

```json
{
  "error": {
    "code": "receipt_not_available",
    "message": "No execution receipt exists for this action because it was not executed."
  }
}
```

Read the action's current status before deciding whether it is pending or will never execute. This response is not a failed receipt or a successful outcome. A missing or out-of-scope action still returns a generic `404`; do not interpret every `404` as `receipt_not_available`. The MCP receipt tool retains its `not_found` tool error.

## Preview a proposal without submitting it

Use `POST /actions/dry-run` to inspect policy decisions and proposed diffs before creating a batch. Use the complete [dry-run request schema](/api/actions/actiondryrunapi/preview-actions) and the same permissions as submission: a Write Workspace key, an active `propose-actions` grant, and `actions.propose`. Upload and creative-duplication previews also require `creative.write`.

Prepare `proposal.json` using the [dry-run reference](/api/actions/actiondryrunapi/preview-actions) and [evidence rules](/mcp/tools#evidence-restrictions). Include `rationale`, `idempotency_key`, and valid evidence even though the preview does not save a proposal. Targets must be human-selected; evidence fields must exist in the fresh server-side capture.

```bash
curl --fail-with-body \
  https://plainrouter.com/api/v1/agent/workspaces/42/actions/dry-run \
  --header "Authorization: Bearer $PLAINROUTER_WORKSPACE_KEY" \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --data-binary @proposal.json
```

A successful request returns HTTP `200`. Use the [dry-run response reference](/api/actions/actiondryrunapi/preview-actions) and inspect **every** action's `status`. An `evaluated` item has a policy prediction, not execution availability or success. `approval_required` and `would_auto_execute` reflect the combined batch prediction, not approval or execution. `diff.before` contains state available to policy evaluation; an empty object or array does not mean a known zero or absent provider object. `diff.proposed` is the normalized action, not a request sent to Meta. A `dry_run_unavailable` item needs a persisted Action row and has a reason instead of a policy prediction or diff. HTTP `200` alone does not mean every action was evaluated.

The preview can read real account and provider state. It does not create a batch, action, decision receipt, or proposal audit event, queue execution, or write to Meta. It uses the current policy or unsaved defaults when no policy exists.

Repeating a preview evaluates current state again; the required idempotency key does not reserve a proposal or freeze the result. If you choose to submit, use the proposal endpoint below with the intended body. Submission reevaluates the proposal and creates its review record. A dry run cannot enable a closed action workflow or override the workspace approval mode.

## Submit a governed proposal

Use the [generated proposal request reference](/api/actions/actionproposalapi/propose-actions) for the typed action input and response fields. A batch contains 1–25 actions and 1–3 evidence declarations. Select targets yourself and include rationale for each action; supply `account_id` when account selection requires it.

Prepare `proposal.json` using the [proposal reference](/api/actions/actionproposalapi/propose-actions) and [evidence rules](/mcp/tools#evidence-restrictions). For creative work, follow the [paused-variant walkthrough](/actions/creative-workflow). Do not invent target IDs, asset IDs, or evidence. Submission also requires `actions.propose`; upload and creative-duplication proposals require `creative.write`.

```bash
curl --fail-with-body \
  https://plainrouter.com/api/v1/agent/workspaces/42/actions \
  --header "Authorization: Bearer $PLAINROUTER_WORKSPACE_KEY" \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --data-binary @proposal.json
```

A new batch returns `201`; an idempotent repeat returns `200` with the existing result. Preserve the original idempotency key for the same intent after a timeout. Read the [proposal response reference](/api/actions/actionproposalapi/propose-actions) for its fields; `approval_queue_url` remains a compatibility alias for `inbox_url`.

In Ask mode, send the reviewer to **Inbox**. Use the reads above to follow the result in either mode. These routes do not approve or reject proposals, edit policy, manage keys, or override the workspace's approval mode. In **Ask**, allowed changes wait for human approval; **Full** can queue them automatically. Historical **Suggest only** approval ends without execution. A successful proposal response is not proof of a provider change or **Landed** status.

The [public MCP server card](https://plainrouter.com/.well-known/mcp/server-card.json) publishes the shared proposal schema. A schema-accepted action type alone does not establish that its execution workflow is available.

## Why is a management target refused?

A submitted batch can contain only one management change per target type and ID across `pause`, `resume`, `increase_budget`, and `decrease_budget`. Repeating it returns HTTP `422` with `action_target_repeated` in the field message for `actions.N.target_entity.id`. Remove the conflicting action; changing its name or idempotency key does not make it a different target.

A target held by an outstanding management proposal is also refused. The message identifies the existing batch. Open that batch in [Inbox](/actions/review-proposals), follow its execution or recovery, and wait for it to settle. If it is still awaiting a decision, an authorized person can review or reject it. Do not create replacement proposals to bypass work already in progress. These constraints also apply to MCP submissions and the Campaigns controls; creation actions sharing a parent destination are a different case.

## Troubleshoot a request

| Result | What to check |
| --- | --- |
| `401` | Key type, expiry/revocation, active principal and connection, and the issuer's current role. The issuer losing permission can invalidate a previously working key. |
| `403` | The active grant must cover `propose-actions`, including for reads. A normal Read key does not qualify. Check any additional proposal permission. |
| `404` | Workspace/account scope and returned action or batch ID. For receipt reads, inspect the error code: [`receipt_not_available`](#what-does-receipt_not_available-mean) describes a visible action without an execution receipt. Out-of-scope records are not exposed. |
| `422` | Account selection, status/page values, and [proposal field errors](/mcp/tools#validation-and-retry-keys). Correct the named field before retrying. |
| `200` with `dry_run_unavailable` | The preview could not evaluate an action without a persisted row. Do not treat it as a passing policy result. |
| Empty `data` | Clear the status filter and confirm the selected account. An empty page does not prove the workspace has no action history. |

The equivalent [five MCP read tools](/mcp/tools#read-actions-and-policy) use the same scoped records and output shapes. MCP tool errors follow the MCP protocol rather than this HTTP status table.
