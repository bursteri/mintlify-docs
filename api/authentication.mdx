Plainrouter uses a per-workspace Server secret for the Signals Conversion API, a
Workspace key for production MCP tool calls and the Actions API, a Management key for developer
management operations, and a separate OAuth management credential for account discovery. Public MCP
discovery and the synthetic MCP sandbox require no credential. Retrieving a production prompt requires a workspace key.

The Signals REST endpoints, TypeScript, Python, Ruby, Go, and the CLI are six interfaces to the same
Conversion API and all use the same Server secret.

## Which credential should I use?

| Goal | Interface | Credential | Scope |
| --- | --- | --- | --- |
| Send or read Signal data | REST, TypeScript SDK, Python SDK, Ruby SDK, Go SDK, or CLI | Server secret | One workspace and its Signals resources |
| Test an MCP integration with synthetic data | `https://plainrouter.com/mcp/sandbox` | None | Four sandbox-only tools; no tenant data or provider access |
| Call Plainrouter tools as an agent | MCP or an authorized workspace route | Workspace key | One workspace, Read or Write tier, and an eligible account selected per account-scoped call |
| Submit or inspect Actions | [Actions API](/api/actions) and [MCP Actions reads](/mcp/tools#read-actions-and-policy) | Write Workspace key with an active `propose-actions` grant, including for reads | One workspace and selected eligible account |
| List accessible workspaces and manage your workspace keys | [Management API](#how-do-i-use-the-management-api) | Management key | Limited by its owner's current access and role; not an MCP credential |
| Discover the approved agent context | `GET /api/v1/agent/context` | OAuth management credential | Read-only account discovery |
| Manage tokens, policies, or approvals in the dashboard | Browser session | Signed-in person's current workspace role | Interactive UI only |

These credentials are not interchangeable. The Conversion API rejects Workspace keys and OAuth management credentials. MCP rejects Server secrets, Management keys, and OAuth management credentials.

<Warning>
  Never paste any Plainrouter credential into an agent prompt. Inject credentials
  through your server-side secret manager or the client's protected credential
  configuration.
</Warning>

## How do I authenticate the REST API?

Send the Server secret as a bearer token to the server-side Conversion
API at `https://plainrouter.com/api/v1`:

```bash
curl "https://plainrouter.com/api/v1/dashboard/events" \
  --header "Authorization: Bearer $PLAINROUTER_TOKEN" \
  --header "Accept: application/json"
```

`PLAINROUTER_TOKEN` must contain the Server secret. A missing or
invalid secret returns HTTP `401`.

For action proposals, status, policy, and decision receipts, use the separate [Actions API authentication and account-selection steps](/api/actions#before-you-start).

## Where do I manage the Signals API secret?

Sign in as the workspace owner, select the intended workspace, and open **Settings → Workspace → Server secret** after Signals is configured. This secret authenticates Signals REST, SDK, and CLI calls; [workspace keys](/mcp/workspace-tokens) have their own **Settings → Workspace keys** page.

### Rotate without interrupting your integration

1. Choose **Rotate** and copy the replacement immediately into your server-side secret manager. The replacement is shown once.
2. Update each integration and verify a read request, such as the event-list request above, with the replacement. Your current secret continues working while a replacement is pending.
3. Choose **Confirm** after all integrations use the replacement. Confirmation retires the previous secret.

### Discard a pending replacement

If you lose the replacement before finishing rotation, choose **Discard**, then confirm **Discard pending replacement**. This cancels only the pending secret; your current secret keeps working. **Cancel** or Escape closes the dialog without discarding anything.

Anything already using the pending replacement will stop authenticating after you discard it. Restore those integrations to the current secret before discarding, or prepare to update them during a new rotation. Then choose **Rotate** again, save the new replacement, verify it, and **Confirm** when ready. The page cannot reveal a lost secret again.

After discarding, **Replacement pending** disappears and **Rotate** becomes available. Verify a read with the current secret if you need to confirm integration access. Discard does not change the publishable browser key or the current server secret.

### Revoke a lost or exposed secret

Choose **Revoke** and confirm the warning. The current secret and any pending replacement stop working immediately, and Plainrouter issues a new secret. Copy it once, update your integrations, and verify authentication again. Expect old credentials to return `401`.

Use **Discard** when only the pending replacement should be canceled. Use **Revoke** when the current secret must stop working, including when it is exposed. Keep secrets out of browser code. The [Signals snippet](/signals/install-pixel) uses a publishable key instead.

## How do I authenticate the TypeScript SDK?

Install `@plainrouter/sdk@0.5.1`, then configure the generated client explicitly:

```ts
import {
  configurePlainrouter,
  listEvents,
} from "@plainrouter/sdk";

configurePlainrouter({
  signalTrackerSecret: process.env.PLAINROUTER_TOKEN!,
});

const result = await listEvents({
  query: { per_page: 25 },
});
```

The TypeScript SDK does not read environment variables automatically. Your
server must pass the Server secret through `signalTrackerSecret`.
The property keeps its pre-collapse name for compatibility.

## How do I authenticate the Python SDK?

Install [`plainrouter==0.5.2`](https://pypi.org/project/plainrouter/), then create a client with the Server secret:

```python
import os

from plainrouter import create_client, list_events

client = create_client(os.environ["PLAINROUTER_TOKEN"])
response = list_events.sync(client=client)
```

The Python SDK requires Python 3.11 or newer. Each operation module also exposes
an asynchronous `asyncio` method.

## How do I authenticate the Ruby SDK?

Install [`plainrouter-sdk 0.1.1`](https://rubygems.org/gems/plainrouter-sdk), then create a client with the Server secret:

```ruby
require "plainrouter"

client = PlainRouter::Client.new(
  token: ENV.fetch("PLAINROUTER_TOKEN")
)

events = client.operations.list_events(per_page: 25)
```

The Ruby SDK requires Ruby 3.2 or newer. The client sends the supplied tracker
secret as a bearer token and does not read environment variables automatically.

## How do I authenticate the Go SDK?

Install `github.com/plainrouter/sdk-go@v0.5.2`, create the generated client, and attach the Server secret to the request context:

```go
config := plainrouter.NewConfiguration()
client := plainrouter.NewAPIClient(config)
ctx := context.WithValue(
	context.Background(),
	plainrouter.ContextAccessToken,
	os.Getenv("PLAINROUTER_TOKEN"),
)

report, _, err := client.OperationsAPI.GetEmqReport(ctx).Execute()
```

The Go SDK requires Go 1.23 or newer. Keep the Server secret in server-side credential storage.

## How do I authenticate the CLI?

The CLI uses the same Server secret. Current `0.5.x` builds call it a
tracker token in prompts for compatibility. Store it through the hidden login
prompt for an interactive workstation:

```bash
plainrouter auth login
plainrouter auth status
plainrouter events list --json
```

For CI or an ephemeral shell, inject `PLAINROUTER_TOKEN` through the job's secret
manager before running the command. The CLI does not expose a `--token` option.
An environment token takes precedence over the locally stored token.

## How do I try MCP without a credential?

Connect an MCP client to the synthetic test endpoint:

```text
https://plainrouter.com/mcp/sandbox
```

It exposes `get_account_state`, `get_signal_health`, `get_performance`, and
`validate_sandbox_event`. Every response is synthetic and marked with
`"sandbox": true`. The endpoint reads no tenant data, persists nothing, and
contacts no advertising provider.

The production endpoint also permits anonymous protocol discovery, tool and
resource and prompt listing, and reads of static `ui://` app shells. Retrieving a prompt with `prompts/get` and calling a production tool require a valid workspace key. Account-scoped reads also require access to the selected account.

## How do I authenticate Plainrouter MCP?

Configure an MCP-compatible client with these exact connection values:

| Setting | Value |
| --- | --- |
| Transport | Remote HTTP |
| Server URL | `https://plainrouter.com/mcp` |
| Authorization | `Bearer <workspace-execution-token>` |

A workspace owner or member creates a key in **Settings → Workspace keys** for one workspace,
a Read or Write tier within their current role, and a 30, 90, or 365 day expiry.

For account-scoped work, call `get_account_state` first. Confirm the returned workspace and Meta ad
account before continuing. For installation before connecting Meta, use [`get_install_instructions`](/mcp/tools#get_install_instructions) and confirm its workspace. Use `account_id` when the workspace has multiple eligible active accounts. Older
account-bound keys cannot override their binding. See [account selection](/mcp/workspace-tokens#how-does-account-selection-work).

<Warning>
  A Write or Admin token can submit governed proposals, but it does not bypass
  policy, human approval, provider verification, or account restrictions. A
  proposal-producing MCP request is not a direct Meta write.
</Warning>

## Where do I create a Management key?

Open **Settings → Management keys**, enter a name, select a 30, 90, or 365 day expiry, and choose **Create key**. Copy it once into developer-side secret storage. Use **Delete** to remove an obsolete key. The table shows creation, last use, expiry, status, and **Created by**; a team owner can manage team members' keys where permitted.

Management keys authenticate the four management operations below under the key owner's current membership and role. Give agents a workspace key for MCP instead. A Management key is not the OAuth management credential described below and cannot authenticate the agent-context route, Signals Conversion API, or human approval pages.

## How do I use the management API?

Use a Management key to list accessible workspaces and create, list, or revoke **your own** workspace keys. These operations do not create workspaces or change ads. The `/tokens` paths retain their API name even though the dashboard calls the credentials workspace keys.

Before starting, [create a Management key](#where-do-i-create-a-management-key), load it into `PLAINROUTER_MANAGEMENT_KEY` through your secret manager, and confirm your current membership in the workspace's team. Do not use a workspace key or browser session as the management API credential.

Use the base URL `https://plainrouter.com/api/v1` for these paths:

| Method | Path | Result |
| --- | --- | --- |
| `GET` | `/management/workspaces` | `200` with `workspaces`: workspace IDs, names, and team IDs/names for your current memberships and owned teams. |
| `GET` | `/workspaces/{workspace}/tokens` | `200` with `access_tokens`: your keys in that workspace, including revoked records, without plaintext secrets. |
| `POST` | `/workspaces/{workspace}/tokens` | `201` with the new plaintext `token` and `access_token` metadata. |
| `DELETE` | `/workspaces/{workspace}/tokens/{token}` | `204` with no body after revoking your key and its grant. |

### 1. Find the workspace

```bash
curl --fail-with-body https://plainrouter.com/api/v1/management/workspaces \
  --header "Authorization: Bearer $PLAINROUTER_MANAGEMENT_KEY" \
  --header 'Accept: application/json'
```

Choose the returned workspace's integer `id`. It is different from the advertising-account ID used in MCP calls. The examples below use workspace ID `42`; replace it with your selected ID.

### 2. Create a workspace key

```bash
curl --fail-with-body https://plainrouter.com/api/v1/workspaces/42/tokens \
  --header "Authorization: Bearer $PLAINROUTER_MANAGEMENT_KEY" \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --data '{"name":"Account reporting","tier":"read","expires_in_days":90}'
```

| Field | Accepted value |
| --- | --- |
| `name` | Required string, up to 255 characters. |
| `tier` | `read` or `write`. Write requires current update permission; the workspace owner can issue either tier. |
| `expires_in_days` | `30`, `90`, or `365`. |

The new key is scoped to the workspace and has no fixed ad-account binding. Do not send an account ID when issuing it; follow [account selection](/mcp/workspace-tokens#how-does-account-selection-work) when using it.

The response contains a secret. Capture `token` directly into protected client configuration or secret storage and retain `access_token.id` for lifecycle operations. Plaintext is returned only on creation; the response uses `Cache-Control: no-store, private`. Keep it out of terminal recordings and request/response logs. A repeated POST creates another key; do not treat issuance as an idempotent retry.

Verify the new workspace key with [`get_account_state`](/mcp/tools#get_account_state), supplying `account_id` when required. Confirm the returned workspace and Meta ad account before any proposal. Use the new workspace key for that MCP call, not the Management key.

### 3. List or revoke your workspace keys

```bash
curl --fail-with-body https://plainrouter.com/api/v1/workspaces/42/tokens \
  --header "Authorization: Bearer $PLAINROUTER_MANAGEMENT_KEY" \
  --header 'Accept: application/json'
```

Each `access_tokens` item includes `id`, `name`, `tier`, `abilities`, `last_used_at`, `expires_at`, `revoked_at`, and the historical `rotated_from_token_id`. Listing does not expose another member's keys or recover a secret. Use the token record's integer `id`, not its plaintext value or grant ID, to revoke it:

```bash
curl --fail-with-body --request DELETE \
  https://plainrouter.com/api/v1/workspaces/42/tokens/123 \
  --header "Authorization: Bearer $PLAINROUTER_MANAGEMENT_KEY" \
  --header 'Accept: application/json'
```

Replace `123` with your key's record ID. A successful response has no body. List again to verify `revoked_at` is populated. To replace a key, create and verify its replacement before revoking the old one; there is no rotation endpoint.

Deleting or expiring a Management key does **not** revoke workspace keys it previously issued. Revoke each workspace key separately when access should end. Removing the issuer's membership or reducing their role also changes what their credentials can authorize.

### Why does a management request fail?

| Result | Check |
| --- | --- |
| `401` | Use a live Management key created from the current settings page. Workspace keys, OAuth credentials, expired/revoked keys, and older unmarked personal tokens do not qualify. |
| `403` | Recheck current team membership and whether your role permits the requested tier. Membership is checked on each request. |
| `404` | Check the workspace ID and token ID. Another member's token is not available through your management credential. |
| `422` | Check name, tier, expiry, and that a key being revoked belongs to the selected workspace. |

## How do I use an OAuth management credential?

An OAuth management credential has one documented agent-facing use:

```http
GET /api/v1/agent/context HTTP/1.1
Host: plainrouter.com
Authorization: Bearer <oauth-management-credential>
Accept: application/json
```

The route returns the approved read-only account-discovery context. The same
credential cannot call MCP tools, Launcher imports, or other agent-authenticated
routes. Use a separately issued Workspace key for MCP after
discovery.

## Why does a dashboard URL reject my bearer token?

Dashboard settings and approval pages require a signed-in browser session. A valid Workspace key or OAuth management credential cannot replace that session, even with an active grant or Admin tier.

A bearer header causes `401` on these session routes even when a valid browser session cookie is also present. Remove the `Authorization: Bearer ...` header from browser-session requests; check any proxy or client that adds it automatically. Signing in again does not make a bearer header valid on a session route.

If an automation receives `401` on a dashboard URL, check the requested interface before rotating credentials. Use the documented MCP or API operation with its matching credential, or sign in to complete the interactive action. For grant management, follow [the dashboard revocation steps](/mcp/workspace-tokens#inspect-and-revoke-a-grant-in-the-dashboard) or the separately authorized [`revoke_grant` MCP tool](/mcp/tools#revoke_grant).

The REST contract and all four SDKs expose the signed Conversion API operations. The
PyPI and npm CLI distributions expose nine commands and do not include an ingestion-verification
command. Use REST, an SDK, or MCP for ingestion verification.

## Which credentials must not be confused?

- A Server secret cannot authenticate MCP.
- A Workspace key cannot authenticate the Conversion API.
- An OAuth management credential cannot authenticate MCP.
- A browser session cannot replace an API or MCP bearer credential.
- A same-origin Path B forwarding secret authenticates generated forwarding
  infrastructure only. It is not an API, SDK, CLI, or MCP credential.
- Meta access tokens remain on the Plainrouter server. Do not place a Meta token
  in a Plainrouter client configuration.

For complete request and response fields, use the [Conversion API
reference](/api/conversions). For token tiers and lifecycle, use
[Workspace tokens](/mcp/workspace-tokens). For available agent tools, use
the [MCP tool reference](/mcp/tools). For machine discovery, start
with the [API resource index](/api/resources) or the [RFC 9727
