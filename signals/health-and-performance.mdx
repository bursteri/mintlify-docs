The **Signals** dashboard answers two questions: whether your first-party measurement path is working, and whether stored conversion counts align with Meta's reports.

The page refreshes its stored measurements about once per minute. Opening it does not trigger a live Meta Marketing API request.

## Health states

| State | Meaning | What to do |
| --- | --- | --- |
| **Setup required** | The Signal or first-party hostname is not fully active. | Finish CNAME and HTTPS validation. |
| **Awaiting data** | Setup is active, but Plainrouter has not received a measurement event. | Send a server event or install the optional pixel and visit the live site. |
| **Measurement pending** | Events are arriving, but delivery, EMQ, or reconciliation measurements are incomplete. | Allow the first measurement cycles to complete and watch diagnostics. |
| **Needs attention** | At least one warning or critical diagnostic is active. | Open **Diagnostics** and address each item. |
| **Healthy** | Event flow exists and all required recent measurement categories are present without warnings. | Continue monitoring. |

<Note>
  Event activity alone is not enough for **Healthy**. Plainrouter waits for recent delivery outcomes, an EMQ snapshot, and measurable reconciliation history before claiming measured health.
</Note>

## Summary metrics

### Events received

Arrival activity counts the dedicated arrival records sent once per document load. A consented `PageView`, purchase, or other conversion does not add another arrival. The completed reporting window and **Today so far** are separate; today's value is an incomplete local-day count.

This metric covers collection. It does not mean every event was eligible for or accepted by Meta.

Arrivals stay aggregate-only and do not appear in event-level lists or detail APIs. Their records contain no page URL, referrer, platform or channel source, visitor identity, IP address, user agent, or commerce details. Event time is rounded down to the UTC hour. Arrivals never create destination deliveries, and legacy exposure rows do not enter the new arrival totals. Invalid traffic is excluded.

Privacy-limited display is separate from collection. A strict-EU severed subtotal from one to four arrivals is withheld until it reaches five. If no other component can be shown, the display is **Suppressed (&lt;5)**. If other components can be shown, the displayed number is partial and omits the withheld subtotal. Suppressed and partial values do not mean that collection stopped.

### Match quality

This is the latest stored Meta Event Match Quality score on a 0–10 scale. The trend compares the current snapshot with the prior week when a comparison exists.

The chart appears after at least two stored snapshots.

### Delivery acceptance

This is the percentage of non-test destination deliveries from events received in the last 24 hours that reached an accepted state.

```text
acceptance rate = accepted deliveries / total non-test deliveries × 100
```

The detail separates accepted and failed deliveries. Pending deliveries include queued, sent, and retrying states.

### Verified gap

This compares stored daily reconciliation counts:

```text
observed gap = gateway-verified accepted conversions - Meta-reported conversions
```

- A positive value means the gateway count is higher.
- A negative value means the Meta-reported count is higher.
- Zero means the stored counts match for the selected window.

Alignment uses the larger of the two totals as the denominator. It is unavailable when both totals are zero.

<Warning>
  Verified gap is an observed account/dataset-level count difference. It is not CPA, attribution lift, incrementality, spend, or target-level performance.
</Warning>

## Gateway vs Meta chart

Each row shows one stored daily reconciliation report:

- **Gateway** is the number of gateway-verified accepted conversions.
- **Meta** is the number reported by Meta in the stored reconciliation run.
- The signed number is that day's observed gap.
- An amber gap indicates the day exceeded the configured residual threshold.

If no rows appear, Plainrouter has not stored a daily reconciliation report for the window.

## Arrivals vs platform-claimed clicks

The **Arrivals vs platform-claimed clicks** panel compares customer-visible observed arrivals with account-level clicks reported by the connected platform. It uses the selected complete-day window, shortened when the workspace's Signals retention window does not contain the full period. **Today so far** is shown separately.

| Metric | Meaning |
| --- | --- |
| **Total arrivals** | Valid observed arrival records after the customer-visible privacy rules. Conversion events and legacy exposure rows do not contribute; a withheld component can make the result suppressed or partial. |
| **Platform-claimed clicks** | Clicks stored by Plainrouter during scheduled reconciliation for the same account and daily period. |
| **Difference** | Total arrivals minus platform-claimed clicks. |
| **Difference vs claimed** | The difference as a percentage of platform-claimed clicks. It is unavailable when the claimed-click total is zero. |

The channel table reads consented, attributed conversion-event data separately from arrival totals. It includes global consent rows and full-consent strict-EU rows. Portfolio-scoped, legitimate-interest, severed-measurement, and source-less rows never appear in the channel view. Because arrival records carry no channel identity, the channel rows do not allocate or sum to the total arrival count.

Opening the dashboard or clicking **Export CSV** reads stored data only and does not make a live Marketing API request. Plainrouter reports **Not connected** when no active platform connection exists and **Unavailable** when the retained period is incomplete or stored click history is missing or stale.

## Why numbers differ

Plainrouter arrivals, ad clicks, pageviews, sessions and visitors count different things. A difference between them does not, by itself, measure lost visitors or failed conversion delivery.

### Meta clicks

Compare against the connected Meta ad account's `clicks` metric, not outbound clicks or landing-page views. Plainrouter arrivals can include traffic from other sources, and the ad account may advertise other websites. The totals do not pair individual clicks with individual arrivals.

Match the account, complete dates and timezone shown in the comparison. Check the stored data's availability before treating a missing value as zero. Keep this arrival comparison separate from [Verified gap](/signals/health-and-performance#verified-gap), which compares conversion counts.

### GA4

Choose one GA4 metric and record the report settings. Users and sessions are not arrival counts. For collection troubleshooting, compare web `page_view` events for the same domain, then check tag triggers, filters and consent settings. GA4 can record pageviews on browser-history changes as well as page loads; test these separately. See [Google's page-view definition](https://support.google.com/analytics/answer/9216061).

### Plausible

Keep unique visitors, visits, pageviews and custom-event goals separate. Start with pageviews when checking collection, with the same website, dates, timezone and filters. Repeated pageviews need not represent different visitors. See [Plausible's metric definitions](https://plausible.io/docs/metrics-definitions).

### Check the collection difference

1. Match the metric, website and reporting period before comparing totals.
2. Check your [consent configuration](/signals/overview#consent-behavior) and any privacy-limited values shown by Plainrouter. Arrivals do not wait for consent; conversion events and the channel breakdown do. Keep these counts separate.
3. Test one page load and one in-app navigation with your actual consent choices. Confirm which requests reach each collector using the [installation checks](/signals/install-pixel#verify-the-installation).
4. Inspect duplicate tags, redirects and blocked requests. Record the settings and request outcomes needed to reproduce an unexplained change.

Compare GA4 and Plausible using their own reports alongside Plainrouter. The platform-claimed-clicks panel reads stored Meta data; it does not reconcile those analytics reports.

## Diagnostics

Diagnostics explain the state behind the summary. Common messages include:

| Diagnostic | Meaning |
| --- | --- |
| **Collection setup is incomplete** | The Signal or collection certificate is not active. |
| **Waiting for the first event** | No server or browser measurement event has arrived yet. |
| **No events received in 24 hours** | Historical events exist, but recent collection stopped. |
| **Meta comparison is not active** | No active Meta destination is connected. |
| **Delivery measurement pending** | Events exist, but no recent delivery outcome exists. |
| **Meta deliveries are failing** | One or more non-test deliveries failed in the last 24 hours. |
| **Match quality measurement pending** | No stored EMQ snapshot exists yet. |
| **Match quality dropped** | The latest EMQ snapshot crossed the configured week-over-week alert threshold. |
| **Reconciliation measurement pending** | No measurable report history exists yet. |
| **Reconciliation measurements are stale** | The latest report is more than 48 hours old. |
| **A reconciliation gap needs review** | At least one day exceeded the configured residual threshold. |

## Measurement freshness

Reconciliation normally runs daily. Plainrouter marks history stale after 48 hours. Until a recent report exists, the read is `not_measurable` and its quantitative values cannot be cited as evidence for an Actions proposal.

The **Measurement state** panel shows the connected domain, dataset ID, last event, and the time the health response was generated.

## Troubleshoot by symptom

<AccordionGroup>
  <Accordion title="No events received in 24 hours">
    Confirm the snippet still loads from the collection domain. Check `/v1/arrival` for arrival collection and `/v1/events` for consented conversions, then review recent deployment changes, your content security policy, and the workspace's allowed website domain.
  </Accordion>
  <Accordion title="Meta deliveries are failing">
    Reconnect Meta if access changed or expired. Confirm the intended dataset is still available, then review whether failures continue on new events.
  </Accordion>
  <Accordion title="Measurement remains pending">
    Confirm events are arriving and Meta is connected. Delivery outcomes need eligible consented events. EMQ and reconciliation also require their scheduled measurement jobs to create stored snapshots and reports.
  </Accordion>
  <Accordion title="Gateway and Meta differ">
    Review the affected dates and event types. Check consent-skipped events, pending or failed deliveries, late reporting, deduplication, and any duplicate integration that still sends to the same dataset.
  </Accordion>
</AccordionGroup>

## Delete a Signal

Workspace owners can delete a Signal from the delete control in the Signal health header.

Deletion first deactivates collection and removes the hostname from Plainrouter's edge mapping. It then deletes the Signal and its related events and destination configuration. You can create a new Signal afterward, but the deleted Signal cannot be restored from the dashboard.

<Warning>
  Deleting a Signal is permanent. It does not retract events that a destination already accepted. Use the destination's own privacy controls or support process for data already held there.
</Warning>
