Connect your Meta dataset to Plainrouter to deliver consented Signals events through the managed browser Pixel and Meta Conversions API. First authorize the relevant Meta assets, then select the dataset and verify delivery. A saved dataset under **Meta delivery** confirms the destination configuration; it does not prove that a conversion has reached Meta.

This guide covers Plainrouter's managed integration. For integration choices, start with the [Meta Conversions API overview](https://plainrouter.com/library/meta-conversions-api). If you are writing directly to Meta instead, use [Meta's direct-integration training](https://www.facebookblueprint.com/student/path/219714-set-up-implement-verify-conversions-api).

## Before you begin

You need:

- A workspace with its website address saved in [Signals setup](/quickstart). You can connect Meta before installing the collection domain; delivery checks require a working installation.
- Workspace-owner access in Plainrouter.
- Access to the required Meta Business assets, Meta ad account, and dataset, with permission to grant Plainrouter access.
- The [current Signals snippet](/signals/install-pixel) and a [consent integration](/signals/track-events#set-consent) for browser conversions.
- For backend conversions or API tests, a server-held [Signals workspace secret](/api/authentication#how-do-i-authenticate-the-rest-api).

An identity-free arrival does not require a Meta connection and never triggers Meta delivery. Advertising conversion events require the supported consent grant.

## Connect Meta for reporting

Open **Connections → Ad accounts → Meta** and choose **Connect Meta**. The Signals overview also links to Connections. Complete Meta authorization, then under **Choose the Meta account to bind**, choose the **Business portfolio** and active **Ad account** and select **Confirm account**. Signals uses the selected account for its stored platform activity.

This reporting connection is separate from selecting a conversion destination. Connecting an ad account alone does not prove that a Pixel is configured or that conversions are being delivered.

Connections also has separate **Google Ads**, **Stripe**, and **Site snippet** sections. Google Ads reads account spend; its presence does not enable a Google conversion destination. Stripe records [verified Checkout revenue](/signals/track-events#verify-stripe-checkout-settlement). The site snippet section links to installation.

### Who can connect or change an ad account?

Connection permissions depend on the team's current connection for that platform:

| Task | Plainrouter access |
| --- | --- |
| Connect initially, or reconnect when no healthy bound connection exists | Current team member, admin, or owner. |
| Replace a healthy connection or select a different bound account | Team admin or owner. |
| Disconnect the platform | Team admin or owner. |

A healthy Meta binding has an active connection, stored credentials, and a selected ad account. The check covers the team's Meta connections, so switching workspaces does not let a member replace an existing healthy binding. Google Ads uses the same role boundary for its spend connection.

These permissions apply to ad-platform connections. **Meta delivery**, Stripe configuration, and site setup retain their separate workspace-owner controls.

### What does the connection status mean?

The platform card shows `not_connected`, `revoked`, `attention_needed`, or `connected`. Agents receive the same workspace-specific status in [`get_account_state.connection.health`](/mcp/tools#how-should-i-interpret-connection-health). The raw `connection.status: "active"` alone is not a health verdict.

For `attention_needed`, inspect the stored read and connection details, then reconnect when required using the [appropriate team role](#who-can-connect-or-change-an-ad-account). A `connected` status does not prove a recent read or conversion delivery. See the [status table](/reference/statuses-and-terms#provider-connection-health) for each value, and verify Meta delivery separately below.

## Connect the destination

<Steps>
  <Step title="Open Meta setup">
    Open [Connections](https://plainrouter.com/connections) for the selected workspace and find **Meta delivery** in the Meta card. Website setup opens Install first; connecting Meta remains optional for arrival collection.
  </Step>
  <Step title="Authorize Meta">
    Complete Meta's authorization flow and grant access to the intended Meta ad account and dataset.

    Meta access tokens stay on the server. Do not add a Meta token or Signals workspace secret to your browser snippet.
  </Step>
  <Step title="Choose a dataset">
    Search the **Meta dataset** picker by dataset name or ID, select the dataset that should receive this Signal's events, then choose **Connect Meta dataset**. The picker gathers accessible datasets from active authorized ad accounts and keeps each dataset associated with its account. Check the selected ID against Meta Events Manager.
  </Step>
  <Step title="Confirm the destination">
    After saving, Plainrouter returns to Connections. Confirm the account and dataset ID under **Meta delivery**. Use **Install** to finish collection-domain setup if needed, then continue with the delivery checks below.
  </Step>
</Steps>

<Warning>
  After validating Plainrouter, remove other Pixel or CAPI integrations that send the same events to this dataset. Independent senders can create duplicate conversions even when each integration works on its own.
</Warning>

### Can I finish Signals setup without Meta?

Yes. Return to **Signals → Install** at any time, including when authorization is unavailable or the dataset list is empty. Finish installation and return to Connections later. For a missing asset, use **Reconnect Meta** and grant access to the intended assets before retrying.

Continuing without Meta does not connect a destination or make conversions eligible for delivery. Verify the [arrival](/signals/install-pixel#verify-the-installation) and [Meta delivery](#how-do-i-verify-meta-delivery) independently.

## How managed delivery works

After `ad_storage`, `ad_user_data`, and `ad_personalization` are all `granted`:

1. The Signals browser library fetches the public dataset ID from your collector.
2. It loads Meta's browser library and sends the browser event.
3. Plainrouter sends the eligible matching server event through Conversions API.
4. The managed pair uses the same event name and event ID for Meta deduplication.

If Meta's browser library is blocked, eligible server delivery can still continue. A missing browser event alone does not establish a server-delivery failure.

For your own backend purchase integration, use a [Plainrouter SDK recipe](/sdk/recipes/meta-conversions) or the [REST API](/api/conversions). Choose one purchase owner: the public `signalq("track", ...)` command generates its own ID and cannot accept your backend's ID. Independent calls can create duplicate purchases. Use the [purchase ownership table and managed example](/signals/track-events#avoid-duplicate-meta-events) before combining senders.

## How do I verify Meta delivery?

Check the stages separately:

| Stage | Check | What the result means |
| --- | --- | --- |
| Website collection | [Inspect the arrival request](/signals/install-pixel#verify-the-installation). | An accepted arrival proves collection receipt, not a Meta conversion. |
| Consented conversion ingestion | Confirm your conversion request succeeds. | `202` means Plainrouter accepted the event for processing. |
| Destination delivery | Open the event's delivery trace through [GET event](https://plainrouter.com/docs/api/events/get), or request the account-scoped [`get_signal_health`](/mcp/tools#get_signal_health) diagnostic through MCP. | `accepted` means Meta accepted that delivery. Pending and failed states require separate interpretation. |
| Browser/server pairing | Inspect the intended dataset in Meta Events Manager and compare the event name and event ID for the pair. | Matching identifiers support deduplication; an API receipt alone does not verify the pair. |

Meta acceptance does not guarantee attribution, an Event Match Quality score, or improved advertising performance. Use [Signal health and performance](/signals/health-and-performance) to interpret stored reporting windows and differences.

### Test without sending a real purchase

Use Plainrouter's destination test operations when you need a controlled Meta-delivery check:

1. Identify the Plainrouter destination you connected. The API's `{destination}` parameter is a Plainrouter destination ID, not your Meta dataset ID.
2. Use [Configure destination test mode](https://plainrouter.com/docs/api/destinations/test-mode) with `enabled: true` and the dataset's Meta Test Events code in `test_event_code`.
3. Call [Send a controlled test purchase](https://plainrouter.com/docs/api/destinations/test-purchase). It creates an identity-free synthetic purchase for that destination while test mode is enabled. This operation contacts Meta.
4. HTTP `200` means Meta accepted the controlled purchase; `502` means Meta did not accept it. Inspect the same dataset's Test Events view separately.
5. Restore destination test mode to `enabled: false` when the check is finished, before resuming normal conversion delivery.

The [identity-free ingestion diagnostic](/signals/verify-ingestion) is a different test: it contacts no destination and cannot prove Meta delivery.

## Refresh available assets

If the intended ad account or dataset is missing, choose **Reconnect Meta** and complete authorization again with access to those assets. Then select the intended dataset and recheck the connection details.

## Troubleshoot

### Connect, Reconnect, or Disconnect is missing

Confirm your current team and role. Members can complete an initial or incomplete connection, but a healthy binding requires an admin or owner to reconnect or change it. Disconnect is also restricted to an admin or owner. Authorization is checked again when OAuth returns; if another member completes a healthy connection while you are authorizing, ask an admin or owner to continue.

### No datasets appear

- Confirm the authorizing Meta user can access the dataset.
- Confirm the dataset belongs to or is shared with the relevant Business portfolio.
- Reconnect Meta with access to the intended assets, then reopen dataset selection.

### Browser Pixel events do not appear

- Confirm all three advertising consent values are `granted`.
- Check whether a content blocker prevents `connect.facebook.net` from loading.
- Check your site's [Content Security Policy](/signals/install-pixel#content-security-policy).
- Confirm you are inspecting the connected dataset and a conversion event, not an arrival.

### Server delivery needs attention

Start with the [worked event trace](/api/conversions#read-a-failed-delivery-trace). `queued`, `sent`, and `retrying` are pending; let delivery complete before taking further action. For `failed:auth`, [reconnect the intended assets](#refresh-available-assets), then [replay the eligible delivery](/api/conversions#how-do-i-replay-a-failed-delivery) using its numeric delivery ID.

A consent-skipped event is not a transient provider error and is excluded from replay. Fix the [consent integration](/signals/track-events#set-consent) for future eligible events. Reposting an existing event ID only returns the original ingestion receipt; it does not restart destination delivery. Use the [status reference](/reference/statuses-and-terms#destination-delivery) for other failures.

### Meta shows duplicate purchases

Inventory every integration that sends the purchase, including a theme Pixel, tag manager, commerce plugin, and backend. Keep one intended browser/server pair with matching event names and IDs. Do not generate a fresh ID on every retry. Follow the [missing and duplicate events checklist](https://plainrouter.com/library/meta-capi-missing-duplicate-events).

### The controlled test returns `422`

Confirm test mode is enabled for the same Plainrouter destination and inspect the response's field errors. A `404` instead means the destination was not found in the authenticated workspace.
