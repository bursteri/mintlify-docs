Use `signalq` to pass your consent platform's current decision to Signals and send business events. The examples below use the full advertising-consent path; eligible global policy has a separate [legitimate-interest boundary](/signals/overview#how-does-the-global-policy-differ). With a connected Meta dataset, one browser `track` call supplies the managed Pixel and server event with a shared ID.

## Before you begin

- [Install the generated Signals pixel](/signals/install-pixel) once and keep its `init` call before consent and event calls.
- Choose a consent source: a supported external signal, an explicit CMP adapter, or the configured Plainrouter fallback card. Verify the actual advertising choices on every page and after changes.
- [Connect Meta](/signals/connect-meta) if you want managed Meta delivery.
- Choose whether the browser, your backend, or Stripe owns each purchase. Follow [Avoid duplicate Meta events](#avoid-duplicate-meta-events) before combining integrations.

Calls made before the asynchronous Signals script loads are queued, but the queue stub returns `undefined`. It does not return the later command's result. Run examples that read an event ID, identification result, or visitor ID only after the generated script's `load` event; register that handler before the script can finish loading. Do not install a second snippet to wait for it.

## How does the snippet choose a consent source?

The current v4 snippet sends its arrival first, then uses a queued explicit `signalq("consent", …)` decision when present. Otherwise it checks supported TCF and Consent Mode signals during a 1.5-second detection window. A detected supported CMP without a usable decision suppresses the fallback; it does not grant consent. Keep the explicit adapter below when your CMP needs one.

If no external source takes precedence, the snippet can restore the saved Plainrouter choice or display the enabled fallback consent card. **Accept all**, **Reject all**, and **Customize** record different decisions. In the current card, **Analytics** controls `analytics_storage`; **Marketing** controls `ad_storage`, `ad_user_data` and `ad_personalization`. The consent-based advertising path requires all three advertising grants. Selecting only Analytics does not grant Marketing. Previously saved v1 choices keep their original meaning rather than being reinterpreted as new choices.

A later valid external decision dismisses the fallback. The `pr_consent` cookie stores the Plainrouter choice; it is separate from visitor measurement identifiers. To reopen the card from your own preferences control, use:

```js
window.plainrouter("consent", "open");
```

This command opens the supported consent surface; it does not itself grant permission. Call it after the snippet loads and wire it to a visitor action. The fallback remains subject to its configured enablement and market policy. Set its banner and floating reopen options in [Signals → Install](/signals/install-pixel#can-i-enable-the-included-consent-banner). Use [Cookie scan](/signals/cookie-scan) to check unrelated pre-consent scripts, and [Consent choices](/signals/consent-choices) to read recorded decisions when available.

If the workspace owner selects **Off — I handle consent myself**, manual opening and the floating Privacy settings button are disabled too. Stored decisions still apply. Follow the [website-snippet and vendor-tag migration steps](/signals/install-pixel#what-must-i-change-when-turning-the-banner-off); your CMP must provide defaults, saved choices, updates and withdrawal.

For verification, use a fresh browser context: test full acceptance, rejection, a partial Customize choice, a returning saved choice and withdrawal. Check actual event requests and [destination delivery](/signals/connect-meta), not just whether a card appeared. A blocked config request or detected CMP without a decision can leave advertising events silent. Do not turn that unknown state into a grant.

## Set consent

Connect `signalq` to your consent-management platform. Send the current advertising consent state after initialization and whenever the visitor changes it.

```js
await signalq("consent", {
  consent_basis: "consent",
  consent: {
    ad_storage: "granted",
    ad_user_data: "granted",
    ad_personalization: "granted",
    captured_at: new Date().toISOString(),
    source: "your_cmp"
  }
});

// If the visitor later withdraws consent:
await signalq("consent", {
  consent_basis: "consent",
  withdrawn: true
});
```

Each permission accepts `granted`, `denied`, or `unknown`. Missing or unrecognized permissions remain `unknown`; Plainrouter never upgrades them to a grant.

You can provide one or more supported consent adapters:

| Input | Use |
| --- | --- |
| `consent` | Send Plainrouter's explicit three-permission snapshot. |
| `consent_mode` | Map Google Consent Mode v2 fields. |
| `tcf` | Map a TCF v2 string and optional capture time. |

When you provide more than one adapter, their derived permission states must agree.

<Warning>
  Do not infer consent. Leave each permission `unknown` until your consent-management platform has an explicit choice.
</Warning>

On the consent-based path, conversion events, visitor-cookie access, identity transmission and managed Meta delivery require all three permissions to be `granted`. Granting `ad_storage` alone is insufficient. The identity-free arrival sent once at document initialization is a separate request and does not wait for these permissions. See [What happens on initialization](/signals/install-pixel#what-happens-on-initialization).

A complete grant creates or refreshes the first-party identifiers used for session joins and eligible destination delivery. Leaving full consent stops event transmission and clears the current page's consent-dependent identifiers. Explicit storage denial or withdrawal also discards the in-memory landing context. Send the latest structured state whenever the visitor's choice changes.

On a returning page, the arrival is sent while your consent platform restores its decision. Plainrouter does not read visitor cookies or send conversion events during that undecided period. Existing cookies are not read or refreshed merely because the snippet initialized.

### Connect Cookiebot callbacks

Install Cookiebot on the same page. This adapter uses [Cookiebot's consent properties and browser events](https://www.cookiebot.com/en/developer/). Use it only when your configured **marketing** choice covers all three Plainrouter advertising permissions. For separate choices, map each permission individually with the structured snapshot above.

Place this code once after your generated `init` call. It handles an already-restored choice and later CMP events. Automatic or implied consent stays `unknown`; only an explicit response can grant permissions.

```js
function syncCookiebotConsent() {
  const cmp = window.Cookiebot;
  const explicit = cmp?.hasResponse === true &&
    cmp.consent?.method === "explicit";
  const marketing = cmp?.consent?.marketing;
  const permission = explicit && typeof marketing === "boolean"
    ? (marketing ? "granted" : "denied")
    : "unknown";

  window.signalq("consent", {
    consent_basis: "consent",
    consent: {
      ad_storage: permission,
      ad_user_data: permission,
      ad_personalization: permission,
      captured_at: new Date().toISOString(),
      source: "cookiebot_marketing"
    }
  });
}

for (const event of [
  "CookiebotOnConsentReady",
  "CookiebotOnAccept",
  "CookiebotOnDecline"
]) {
  window.addEventListener(event, syncCookiebotConsent);
}
syncCookiebotConsent();
```

`captured_at` records when this adapter reads the current decision. Retain your CMP's consent record separately. Do not replay purchases from these callbacks: restored consent and multiple CMP events can call the adapter more than once.

For a custom withdrawal button, notify Signals immediately as well as withdrawing in Cookiebot. Attach this function to your site's existing consent-withdrawal control:

```js
function withdrawAdvertisingConsent() {
  window.signalq("consent", {
    consent_basis: "consent",
    withdrawn: true
  });
  window.Cookiebot.withdraw();
}
```

Keep the consent bridge running when consent is denied so it can report changes. Check your CMP's script-blocking configuration if callbacks never reach Signals.

A denial received through a supported TCF or Consent Mode listener cancels an earlier grant still waiting for configuration or consent resolution. That earlier grant must not resume transmission later. After transmission has started, a supported external CMP denial triggers withdrawal in strict workspaces as well as global workspaces. Test the listener your site actually uses; a banner's visual state alone does not establish that Signals received the change.

### Verify grant, partial consent, and withdrawal

Use a development or test site and inspect its Network panel. Test the installed library, not just the pre-load queue. Include grant → denial while configuration is delayed, and grant → transmitted event → denial on an initialized page. After restoring network access, confirm the earlier grant does not resume event transmission. A successful arrival is a separate initialization check and can appear in every row below.

| Current choice | Expected Signals behavior |
| --- | --- |
| CMP not ready, missing permissions, or implied choice in the Cookiebot adapter | No conversion transmission; `track` resolves to `null`. |
| All three advertising permissions granted | Consented `PageView` on entering a grant; subsequent `track` calls can reach the collector. |
| `ad_storage: "granted"`, with `ad_user_data` or `ad_personalization` denied or unknown | No conversion transmission. A storage grant alone is insufficient. |
| Full grant followed by denial or withdrawal | New conversions stop; consent-dependent in-flight work is cancelled. This cannot recall requests already received by a destination. |
| Grant while browser configuration is pending, then denial or withdrawal | Held `track` calls resolve to `null` and held `identify` calls resolve to `false`. A later grant does not revive those earlier calls. |
| Returning page with a stored explicit grant | Arrival runs during initialization; conversions wait for the CMP to restore and report the grant. |

For a CMP with separate permissions, exercise a partial choice through its UI and confirm the transmitted snapshot preserves it. Do not replace partial choices with the Cookiebot adapter's shared marketing value.

If the result differs, confirm `init` ran first, inspect the actual three permission values, and check for conflicting adapters. Use [Verify ingestion](/signals/verify-ingestion) to separate a collection problem from consent gating; use [Meta delivery checks](/signals/connect-meta#how-do-i-verify-meta-delivery) for destination acceptance.

## How landing click IDs are handled

The snippet captures supported landing query parameters in the current document's memory: `fbclid`, `gclid`, `gbraid`, `wbraid`, `ttclid`, and `msclkid`. Unknown or partial consent keeps this temporary buffer available for a later complete grant. Explicit storage denial or withdrawal discards it.

Click IDs are sent with eligible events only after full consent. They never enter the identity-free arrival payload. The browser no longer reads or writes the legacy `pr_click_ids` value; it expires that cookie when full consent opens and when an active grant is withdrawn. A new document starts with its own landing context.

The Meta `_fbc` and `_fbp` cookies are separate from this retired click-ID map and remain subject to full consent. At event intake, Plainrouter drops invalid or unsupported click-ID entries individually while retaining valid entries. Do not rely on one malformed value to reject an otherwise valid event.

## Track an event

Call `track` with an event name and an optional payload:

```js
const eventId = await signalq("track", "purchase", {
  value: "49.00",
  currency: "EUR",
  order_id: "ORDER-1042",
  num_items: 2
});
```

After the library loads, the promise normally resolves to the event ID after a successful collector response. If page exit switches delivery to a beacon, the ID can be returned without a collector acknowledgement. Check ingestion and destination delivery separately.

It resolves to `null` when full consent is absent, consent changes stop the request, or collection is not accepted after the permitted attempts. Invalid calls, such as a missing event name or a call before `init`, can reject the promise.

The public `track` command generates its own event ID. An `event_id` in the payload or an extra positional argument does not override it. `order_id` is purchase data, not the deduplication key.

<Note>
  Send monetary `value` as a decimal string, such as `"49.00"`. This avoids floating-point ambiguity.
</Note>

### Standard event names

Common names are normalized to Meta's standard spelling. For example, `page_view` becomes `PageView` and `initiate_checkout` becomes `InitiateCheckout`.

Frequently used standard events include:

- `PageView`
- `ViewContent`
- `Search`
- `AddToCart`
- `AddToWishlist`
- `InitiateCheckout`
- `AddPaymentInfo`
- `Purchase`
- `Lead`
- `CompleteRegistration`
- `Contact`
- `Schedule`
- `Subscribe`

Custom event names are trimmed and otherwise preserved.

### Payload fields

These convenience fields move into the event's value data automatically:

| Field | Purpose | Example |
| --- | --- | --- |
| `value` | Monetary value as a decimal string. | `"49.00"` |
| `currency` | ISO 4217 currency code. | `"EUR"` |
| `order_id` | Your unique order or transaction reference. | `"ORDER-1042"` |
| `contents` | Products or items associated with the event. | `[{ id: "SKU-1", quantity: 2 }]` |
| `num_items` | Total item count. | `2` |

You can also provide a `value_data` object directly. Other custom fields remain on the event and are available to supported destinations.

## Identify a consenting visitor

Call `identify` only after your consent policy permits advertising identity use:

```js
const identified = await signalq("identify", {
  email: " Buyer@Example.com ",
  phone: "+358 (40) 123-4567"
});
```

The browser normalizes and SHA-256 hashes email and phone before sending them. Plainrouter never sends the raw email or phone in the identity request. Current v4 also accepts an opaque `external_id` for an app user; it is not an email/phone field and is sent as supplied over the collection transport.

If consent is withdrawn while `identify` waits for browser configuration, the call resolves to `false` and does not resume after a later grant. Obtain current consent and make a new call only when that new identity use is permitted. The same superseding denial cancels a held `track` call with `null`.

- Email is trimmed and lowercased.
- International phone numbers must start with `+` and include 8–15 digits after normalization.
- Finnish local numbers require `defaultPhoneRegion: "FI"` in the initialization configuration.
- Identification returns `false` on an insecure page where browser cryptography is unavailable.

```html
<script>
  window.signalq = window.signalq || function () {
    (window.signalq.q = window.signalq.q || []).push(arguments);
  };
  signalq("init", {
    key: "YOUR_PUBLISHABLE_KEY",
    defaultPhoneRegion: "FI"
  });
</script>
```

### How do I identify an app user in the browser?

After the installed script has loaded and your current policy permits identity use, identify at signup or login with the same stable internal user ID used by your [Stripe association](/signals/track-events#how-do-i-associate-stripe-customers-with-app-users):

```js
const identified = await signalq("identify", {
  external_id: "app_user_1042"
});
```

Use an opaque non-empty string of at most 255 characters, or a safe integer. Avoid email addresses, reusable IDs and IDs that can change. The result confirms the identity request's outcome, not an attributed purchase, a Stripe association or Meta acceptance. Preserve denial, withdrawal and opt-out behavior; do not set a grant merely to make identification succeed.

### How do I subscribe to the canonical visitor join key?

For a custom first-party integration, an authorized workspace manager can enable **Connections → Visitor join key** and choose **Save visitor join key**. This optional setting is disabled by default. Register a callback before the existing event that will carry the grant:

```js
let currentJoinKey = null;

signalq("onJoinKey", result => {
  currentJoinKey = result;
  if (result === null) {
    // Remove any copies held by your integration.
    return;
  }
  // Use visitor_id and captured_at only while this grant remains valid.
});
```

The callback receives `visitor_id`, the original full-grant `captured_at` and a local `revision`, or null on re-init, denial, withdrawal or other loss of eligibility. Keep its state temporary, clear downstream copies on null and handle repeated notifications idempotently. Registration itself sends no request; subscribing after an event waits for the next existing event response, with no cached-key replay.

Release requires the workspace opt-in, an identity-serving first-party transport and full grants for all three purposes. Legitimate interest alone, partial consent, GPC or the shared identity-free tier cannot release a key. Collector enqueue acknowledgement is not proof that downstream core persistence or an order join completed.

The loaded API returns an unsubscribe function; the boot queue does not return that handle. Clear your own copies before unsubscribing. This generic callback does not install a Shopify bridge or configure order webhooks.

## Read the visitor ID

`getVisitorId` returns the current page-local UUID after consent permits it, or `null` while pending or denied. It is not the collector’s canonical visitor join key; use the opt-in [join-key callback](#how-do-i-subscribe-to-the-canonical-visitor-join-key) when that distinction matters.

```js
const visitorId = signalq("getVisitorId");
```

For a custom backend integration, a visitor ID alone is not an advertising consent grant. Follow the [server-event recipe](/sdk/recipes/meta-conversions) and preserve the actual consent decision. Checkout metadata alone does not establish an attributed visitor join. The verified revenue adapter below also applies the effective policy, opt-out and retained-context checks.

## Verify Stripe Checkout settlement

Stripe verified revenue records settled Checkout Sessions and eligible paid subscription renewals. Revenue verification and advertising delivery are separate: an eligible global-policy record can use already-retained customer context, while strict-EU, opted-out or unmatched records do not establish an attributed advertising conversion. `metadata.visitor_id` alone is not proof of a join or Meta acceptance. For your own consented event flow, use the [managed browser purchase](#avoid-duplicate-meta-events) or [backend recipe](/sdk/recipes/meta-conversions).

### What do I need before connecting Stripe?

You need an active Signals workspace, current team update permission for **Connections**, and permission to configure webhook endpoints for the Stripe account that receives your customers' payments. Your application must already create Checkout Sessions and handle order fulfillment. This connection is separate from [paying for Plainrouter](/billing/overview).

The supported settlement flow uses Checkout Session events. Eligible `invoice.paid` renewals use paid, positive-value `subscription_cycle` invoices under a global workspace and effective global policy. A [first paid invoice after a captured trial](#how-are-subscriptions-and-trial-conversions-recorded) has a separate eligibility path; this does not establish support for every Stripe payment flow or invoice. Stripe's [fulfillment guide](https://docs.stripe.com/checkout/fulfillment) explains delayed payments and why returning to a success URL does not prove payment.

### Configure the webhook

1. Open **Connections → Revenue sources → Stripe**.
2. Copy the workspace's **Webhook endpoint** and add it as an endpoint in the intended Stripe account.
3. Use Stripe snapshot events and subscribe to the required list shown in Plainrouter: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `refund.created`, `refund.updated`, `refund.failed`, `customer.created` and `customer.updated`. You can also keep `checkout.session.async_payment_failed` for failure notifications. [Stripe's webhook guide](https://docs.stripe.com/webhooks) explains event formats and endpoint setup.
4. Copy that endpoint's signing secret into **Endpoint signing secret** in Plainrouter and choose **Save secret**. This is the webhook signing secret, not your Stripe API key.
5. Confirm the Stripe card shows `connected`. That status confirms a signing secret is configured; verify a settled payment separately below.

Plainrouter clears the secret field after saving. Use **Rotate secret** when replacing the endpoint's signing secret. **Remove secret** stops webhook authentication until you save a replacement; it does not remove the endpoint from Stripe.

### Associate a Checkout Session with your order

Set `metadata.order_id` to your application's non-personal order ID when creating the Session on your server. Use the same order ID as your browser purchase if both sources report that order. Plainrouter trims this value and uses it as the purchase's order ID; without it, the Checkout Session ID is the fallback. `client_reference_id` does not select Plainrouter's order ID. Keep order IDs within 128 characters so they remain readable.

This request calls Stripe directly, not the Plainrouter SDK. It creates a hosted, one-time Checkout Session. Set the variables from trusted server configuration and an existing order: select the Stripe Price on your server and persist one idempotency key for that checkout attempt. Reuse the key only when retrying the same request. Keep the Stripe secret key server-side.

```bash
curl https://api.stripe.com/v1/checkout/sessions \
  --user "$STRIPE_SECRET_KEY:" \
  --header "Idempotency-Key: $CHECKOUT_ATTEMPT_KEY" \
  --data-urlencode "mode=payment" \
  --data-urlencode "line_items[0][price]=$STRIPE_PRICE_ID" \
  --data-urlencode "line_items[0][quantity]=1" \
  --data-urlencode "metadata[order_id]=$ORDER_ID" \
  --data-urlencode "success_url=https://shop.example/checkout/success" \
  --data-urlencode "cancel_url=https://shop.example/cart"
```

Replace the example return URLs with your application's URLs. Store the returned Session `id` alongside your order and redirect the customer to its `url`. See Stripe's [Create a Checkout Session reference](https://docs.stripe.com/api/checkout/sessions/create) for the complete request. Session creation and the success-page redirect are not payment verification.

### How do I associate Stripe customers with app users?

Use your application's stable internal user ID consistently across server events and Stripe. This lets Plainrouter record a workspace-scoped customer-to-user association when an eligible signed webhook contains both identifiers. Use an opaque ID that is never reassigned and is distinct from an order ID or browser visitor ID. Use the same exact value throughout; do not substitute an email address.

1. Send the signup through your [server-event integration](/api/conversions) with that ID in `user_data.external_id`, preserving the real consent and event fields. The [browser `external_id` command](#how-do-i-identify-an-app-user-in-the-browser) can use the same stable app-user ID when policy permits; neither call proves a Stripe association by itself.
2. When creating Checkout on your server, set `client_reference_id` to the same ID. The signed event must also identify a Stripe Customer. For one-time Checkout that would not otherwise create a Customer, use Stripe's supported `customer` or `customer_creation` option.
3. If you create Stripe Customers directly, set Customer `metadata.user_id` to the same ID and subscribe your workspace endpoint to `customer.created` and `customer.updated`. A signed subscription snapshot can also supply `metadata.user_id`. Plainrouter uses metadata present in the webhook; it does not fetch missing nested Customer or Subscription data.
4. Inspect the signed webhook in Stripe: check the workspace endpoint, Customer ID and selected app-user field. Then verify the retained purchase or lifecycle event separately. HTTP `200` alone does not prove a user association, paid revenue or advertising attribution.

For a Checkout event, Plainrouter checks `client_reference_id` first, then Session `metadata.user_id`, then available nested Customer and Subscription `metadata.user_id`. For a Customer event it reads Customer `metadata.user_id`; for a subscription event it reads Subscription metadata before available nested Customer metadata. Use one consistent ID so these sources cannot disagree.

Add these fields to your server-side Checkout creation request when using an existing Customer. These are Stripe fields, separate from the Plainrouter event body:

```json
{
  "customer": "cus_example",
  "client_reference_id": "app_user_1042"
}
```

Keep `metadata.order_id` for order reconciliation; `client_reference_id` does not replace it. See Stripe's [Checkout Session fields](https://docs.stripe.com/api/checkout/sessions/create) and [metadata propagation rules](https://docs.stripe.com/metadata). Missing Customer data or app-user metadata cannot establish the association. An existing conflicting association is not silently reassigned, and opt-out, erasure and policy boundaries still apply. This setup does not guarantee a browser join, Meta acceptance or attribution.

### How do I verify SaaS setup without creating a paid conversion?

For a managed-hostname (Path A) workspace, call `get_install_instructions` with the authorized workspace. Same-origin forwarding workspaces use their separate [serving setup](/signals/configure-serving); this tool does not return Path B material. Follow `saas_steps` and read `saas_verification`; these are stored-evidence reads, not commands to create a customer, payment or advertising event.

| State | What establishes it |
| --- | --- |
| `setup_ready` | Stored collection evidence, configured Stripe signing secret, recent authenticated Stripe evidence, a retained conflict-free app-user link and an active scoped Meta destination. It does not require a paid conversion. |
| `live_verified` | Setup evidence plus retained live Meta acceptance for an eligible `StartTrial` or `Subscribe`. Synthetic ingestion and test-mode sends do not establish it. |

Inspect each fact's `status`, `value` and `reason`. `observed`, `not_observed`, `test_only` and `unavailable` are distinct. The recent webhook evidence uses the last 24 hours within retention; an ignored webhook, replay or metadata-only update may not leave a new receipt. Missing evidence can also mean erasure or expiry, not faulty setup. Consent receipts are reported separately; neither setup readiness nor missing receipts requires inventing a grant.

Collection evidence can say `browser_snippet` or `server_only`. Keep that distinction: a server observation is not proof that the browser snippet loaded. The installation recipe can still report `pending_release` for its optional browser-identify step; that field does not prove which browser asset your site loaded. Current released v4 supports the [app-user identify call above](#how-do-i-identify-an-app-user-in-the-browser). The server-event path remains available independently; neither path makes a server observation proof of a browser load.

Ask your assistant to read the returned state and [signal quality](/signals/health-and-performance#how-do-i-read-signal-quality-through-mcp), then name the missing evidence and next owner. The workspace owner completes DNS, Stripe secret entry and Meta connection in the app. A setup time estimate is not a deadline for real traffic, billing or live provider acceptance.

### What do StartTrial and Subscribe delivery mean?

Eligible signed Stripe `trial_started` events map to Meta `StartTrial` without monetary value. An eligible `subscribed` event maps to Meta `Subscribe` only after verified first-positive-invoice evidence supplies its value and currency. A status change alone does not prove a paid subscription. Stripe lifecycle delivery uses `action_source: "system_generated"`, not a browser visit, and does not borrow a webhook request’s IP or user agent as customer browser context. Current delivery uses retained, permitted identity context and remains subject to consent, policy, opt-out, destination and freshness checks.

Subscription renewals are not another Meta `Subscribe`, and invoice purchase rows are not sent to Meta as an extra Purchase. `upgraded` and `churned` remain recorded lifecycle facts rather than new Meta delivery promises. Signal quality explicitly labels trial/subscribed Google rows as not sent by design; this does not enable Google delivery.

Use the returned event ID and delivery trace. Do not construct subscription lifecycle event IDs from Stripe IDs: current IDs are workspace-keyed and legacy IDs remain compatibility details. A webhook acknowledgement or recorded lifecycle event is separate from provider acceptance and attribution.

### Is the restricted Stripe revenue key the webhook signing secret?

No. **Connections → Stripe revenue** accepts a restricted read-only Stripe API key and displays its status, live/test mode, account binding and verification reason. The **Stripe** webhook card uses a different endpoint signing secret. [Stripe distinguishes restricted API keys from webhook signing secrets](https://docs.stripe.com/keys). Keep both in their intended app fields and out of MCP prompts, chat, source control and logs.

Saving a revenue key can fail if the account or mode does not match retained signed webhook evidence; a different account or mode requires the app's Signals reset flow. Review the data-removal consequences before resetting. If a key or signing-secret update reports **Stripe credentials are busy. Please try again shortly.**, retry the same intended update later; that message does not mean the new credential was saved.

### Is Stripe history import available to every workspace?

No. History import remains disabled by default and limited to selected workspaces. Connections can show **History import is unavailable for this workspace.** Saving or verifying a revenue key does not enable it, import past subscriptions, prove live event delivery or complete the SaaS installation.

Imported history, where explicitly enabled, stays unattributed and does not change CAC or channel credit. An in-progress or partial run does not establish complete coverage; verified coverage is published only after a completed import. Continue using signed webhooks for the supported live settlement flow above.

### How do I verify a settled purchase?

Inspect the endpoint's delivery in Stripe for a known Checkout Session, then compare the order and amount with Signals. Plainrouter records revenue only when the settlement event has `payment_status` exactly `paid`.

| Stripe state | Expected result |
| --- | --- |
| `checkout.session.completed`, `paid` | Records the paid Checkout Session. |
| `checkout.session.completed`, `unpaid` | No purchase yet; the response reports `pending: true` and `reason: "payment_pending"`. |
| `checkout.session.async_payment_succeeded`, `paid` | Records the settled purchase. |
| `checkout.session.async_payment_failed` | No purchase or refund; reason is `async_payment_failed`. |
| `no_payment_required` | No revenue event; reason is `no_payment_required`. |
| Missing or unknown payment status | No purchase; reason is `unverified_payment_status`. |

An illustrative paid-webhook response is:

```json
{
  "received": true,
  "event_id": "stripe_checkout:cs_example",
  "duplicate": false
}
```

Use the returned `event_id` to find the retained record through [GET event](/api/conversions#how-do-i-confirm-meta-accepted-the-event). For this revenue flow, the check is the purchase record and value, not a Meta `accepted` delivery. A `404` can mean the wrong workspace or that the record is outside read retention.

Duplicate paid notifications for the same Session reuse one purchase record and return `duplicate: true`. The first recorded purchase uses its settlement-confirming webhook's time. An older duplicate can return `duplicate: true` without an `event_id`; do not create another purchase to force a receipt or recover expired payload data. Supported refund notifications record an idempotent negative revenue adjustment. Plainrouter first tries the saved PaymentIntent-to-purchase link in this workspace, then available order metadata and charge references. Purchase lineage is attached only when a matching purchase exists; an unmatched refund does not establish a browser or advertising attribution link. Do not assume Stripe copies Session metadata onto refund objects; see [Stripe metadata propagation](https://docs.stripe.com/metadata).

### How are subscriptions and trial conversions recorded?

Subscribe to all three `customer.subscription.*` events in the setup list so Plainrouter can keep the signed subscription state current. Eligible signed snapshots can record these lifecycle events:

| Plainrouter event | Required Stripe observation |
| --- | --- |
| `trial_started` | A subscription is created as `trialing`, or a signed update changes its status to `trialing`. |
| `subscribed` | A subscription is created as `active`, or changes from `trialing` or `incomplete` to `active`. |
| `churned` | A subscription deletion other than `incomplete_expired`, or an update that changes its status to `canceled`. |
| `upgraded` | An `active` or `trialing` subscription update proves an increase in the comparable recurring monthly total using signed previous values. |

Recovery from `past_due` to `active` is not a new subscription activation. Setting `cancel_at_period_end` alone is not churn. A plan name change, discount, unmatched currency or uncomputable previous price does not by itself establish an upgrade. Plainrouter does not fetch missing historical prices to invent the comparison.

Lifecycle events do not add purchase revenue. Verify paid amounts through Checkout settlement or `invoice.paid` separately. Repeated webhook deliveries must not create another lifecycle conversion; keep the original Stripe event ID when redelivering through Stripe. An ignored or duplicate response is not proof of a new event, and old delivery cannot restore erased identity or expired history. See the [webhook contract](https://plainrouter.com/webhooks.md) and [Stripe subscription events](https://docs.stripe.com/billing/subscriptions/webhooks) for the inputs.

If a lifecycle event is missing, inspect the signed snapshot's event type, current status and `data.previous_attributes`. For upgrades, compare the recurring items, currency and quantities; a larger invoice alone is insufficient. Then inspect the retained event and its destination trace. A lifecycle record is not proof of Meta acceptance or attribution.

For an eligible global-policy subscription Checkout Session with `payment_status: "no_payment_required"`, Plainrouter can retain an available acquisition match for the trial without counting revenue. A later positive, paid `invoice.paid` for that same workspace, Stripe customer and subscription can use that retained match when recording the first paid conversion. This path can accept a first invoice that is not a `subscription_cycle` renewal. Missing matches, strict-EU policy, opt-out or erased identity do not establish advertising attribution; adding `metadata.visitor_id` cannot bypass those checks.

To verify using an existing trial and payment:

1. In Stripe, confirm the workspace endpoint received the subscription snapshot and trial Checkout event. The unpaid trial must not appear as paid revenue.
2. Find the later signed `invoice.paid`. Confirm positive `amount_paid`, `paid: true`, `status: "paid"`, and the matching customer and subscription.
3. Use the webhook response's `event_id`, when supplied, to inspect the retained Signals record. Compare the paid amount and currency, then inspect acquisition and destination evidence separately. A `200` acknowledgement or `subscribed` event alone proves neither a purchase nor Meta acceptance.

If the first payment has no retained trial match, do not manufacture a purchase or resend different metadata to force attribution. Check the workspace, event subscriptions, original identifiers and applicable policy first.

### How are renewals and refund status checked?

For an eligible renewal, inspect the signed `invoice.paid` event: the invoice must be paid, have a positive amount, and use `billing_reason: "subscription_cycle"`. The first paid trial conversion follows the separate checks above; arbitrary invoice events are not equivalent to renewals. A matched prior acquisition can supply retained attribution context; absence of that match does not imply an ad acquired the renewal.

Subscribe to all three refund events above. A succeeded refund can adjust verified revenue; pending, failed or canceled states must not be treated as settled refunds. The **Refund status is unverified** notice means only charge-summary fallback evidence has been observed. Follow its subscription guidance rather than assuming status is confirmed. [Stripe's refund statuses and events](https://docs.stripe.com/refunds) explain the provider side.

When a pending or action-required refund later fails or is canceled, it does not remain counted as a successful refund through an earlier charge summary. Other successful refunds on the same charge remain separate; repeated notifications must not subtract the same refund twice.

Revenue adjustments and downstream advertising delivery remain separate. Inspect the purchase/refund lineage and destination trace; a refund row or a connected Stripe card alone does not prove a platform correction.

### Why is the Stripe purchase missing?

| Symptom | Check or recovery |
| --- | --- |
| Signature rejected with `400` | Check that Plainrouter holds this endpoint's signing secret. After fixing it, resend through Stripe so the delivery has a fresh signature. |
| `received: true` but `ignored: true` | Read `reason`; `workspace_inactive` requires activating the workspace. A successful HTTP response alone is not a recorded purchase. |
| Completed Session, no purchase | Inspect `payment_status` and subscribe to asynchronous success. Do not create a purchase while payment is pending. |
| Paid Session, duplicate response | Inspect the original returned event ID; do not create another Session or purchase to force a new record. |
| Revenue exists but no Meta delivery | This adapter does not establish advertising consent or an attributed visitor join. Review your [purchase owner](#avoid-duplicate-meta-events) before adding another sender. |

Stripe webhook redelivery and [Plainrouter destination replay](/api/conversions#how-do-i-replay-a-failed-delivery) are different operations. Destination replay cannot create a missing Stripe revenue record.

## Reliability behavior

- Event requests use browser `keepalive` where available.
- A granted event still in flight during `pagehide` is also sent as a text beacon.
- Conversion-event requests can receive at most one retry after network failures or retryable responses, within the request's retry budget. Arrival requests are never retried.
- Landing click IDs stay in document memory and are transmitted only with a complete consent grant; the legacy `pr_click_ids` cookie is no longer used for storage.
- First-party browser identifiers can still have shorter lifetimes when a browser applies its own storage restrictions.

## Avoid duplicate Meta events

After you [connect Meta](/signals/connect-meta), continue to track through `signalq`. The managed browser Pixel and Plainrouter server delivery share one event ID.

Choose one purchase owner before adding a confirmation-page event:

| Purchase owner | Event ID and retry behavior |
| --- | --- |
| Browser `signalq("track", "purchase", payload)` | Signals generates one ID for its managed browser/server pair. Built-in transport retries preserve it; another `track` call generates another ID. |
| Your backend using the [Node.js SDK](/sdk/recipes/meta-conversions) or [REST API](/api/conversions) | Your application supplies and persists the ID. Reuse the same ID and purchase payload on retries. A separate `signalq` call does not share it. |
| [Stripe verified revenue](#verify-stripe-checkout-settlement) | Plainrouter derives the canonical purchase from the settled Checkout Session. Choose the intended senders deliberately. If another legitimate source reports the same order, align its explicit order key with Session `metadata.order_id`; do not add another sender merely to force delivery. |

### Send one managed purchase after payment confirmation

Use this recipe when the browser owns the purchase. Your application must first confirm payment on its server and supply the paid order's non-personal string ID, decimal total, currency, and item count. A success URL alone is not proof of payment.

Run this code after the Signals script loads and your CMP has reported the full grant. The map shares one attempt between repeated callbacks for the same order in the current document:

```js
const purchaseAttempts = new Map();

function trackConfirmedPurchase(paidOrder) {
  if (!purchaseAttempts.has(paidOrder.id)) {
    const attempt = window.signalq("track", "purchase", {
      order_id: paidOrder.id,
      value: paidOrder.total, // Decimal string, such as "49.00".
      currency: paidOrder.currency,
      num_items: paidOrder.itemCount
    });
    purchaseAttempts.set(paidOrder.id, attempt);
  }
  return purchaseAttempts.get(paidOrder.id);
}

// Call from your app's confirmed-payment handler, after consent is ready.
// paidOrder comes from your server's verified order response.
const eventId = await trackConfirmedPurchase(paidOrder);
if (eventId === null) {
  console.warn("Purchase unconfirmed. Check consent and delivery.");
}
```

This guard lasts only for the current document. A reload, another tab, or a different sender can still create another purchase. If the same order must survive reloads or job retries with a stable ID, use the backend recipe instead. Do not wrap `track` in an automatic retry loop: an uncertain response can follow an accepted request, and a new call creates a new ID.

The managed flow sends the browser `Purchase` with Pixel `eventID` and submits the matching server `Purchase` with `event_id`. You do not need an additional `fbq` or backend purchase call. Passing the returned ID to another API request does not enrich the already-accepted event.

### Check the purchase pair

1. Confirm the order was paid and the CMP reported all three grants before tracking.
2. Inspect the conversion request's `event_id`, `event_name`, and value data. Internal retries should retain the same ID.
3. Check the event's destination delivery trace, then compare the browser and server names and IDs in the intended Meta dataset. [Meta's deduplication guide](https://developers.facebook.com/docs/marketing-api/conversions-api/deduplicate-pixel-and-server-events/) explains the matching fields.
4. If duplicates remain, inventory confirmation-page handlers, tag-manager tags, theme Pixels, commerce plugins, Stripe webhooks, and backend jobs. Remove overlapping senders after validating the intended flow.

An accepted collector request proves ingestion. It does not establish that Meta received both sides, deduplicated the purchase, or attributed it to an ad. See [How do I verify Meta delivery?](/signals/connect-meta#how-do-i-verify-meta-delivery).
