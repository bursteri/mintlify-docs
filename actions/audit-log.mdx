Open **Audit** from the Plainrouter sidebar to read past action records for the current workspace. Use **Actor** and **Outcome** to narrow the on-screen list, or **Download JSON** to inspect the underlying workspace audit events.

You need a signed-in browser session with access to the workspace. Select the intended workspace before investigating a proposal or exporting its history.

## Filter action history

Each row summarizes an action and its outcome. Select an **Actor** or **Outcome** to narrow the list, and scroll to load older records. The list is an action summary, not a row for every security or lifecycle event.

If the list is empty, clear the filters and confirm the workspace. Token, grant, and policy events may exist in the export even when there are no matching action rows.

## Download workspace audit events

Choose **Download JSON**. The response contains a `data` array of workspace audit events ordered by `sequence`. This export includes the workspace's event history; the on-screen Actor and Outcome filters do **not** restrict it.

Each exported event includes:

- `event_type`, `summary`, actor type, ID, and name.
- `workspace_id`, and related `action_batch_id` and `proposed_action_id` when applicable.
- Structured `payload` and `created_at`.
- `sequence`, `event_hash`, `previous_hash`, and `hash_version`.

Search the export by batch or action ID to follow a proposal across multiple events. Treat the file as workspace data: it can contain actor identities and action details. Token lifecycle events contain metadata, not plaintext credentials.

## Download an action decision receipt

For an action with a stored decision receipt, its Audit row shows **Download decision receipt**. Select it while signed in to the same workspace. This downloads the persisted decision record for that action; **Download JSON** remains the separate workspace event export.

The receipt response contains three top-level fields:

| Field | Meaning |
| --- | --- |
| `document` | The recorded action, target, proposer and approval context, available policy/evidence snapshots, provider receipt details, terminal status, and verification result. |
| `document_sha256` | SHA-256 digest of the canonical document representation, not the downloaded file's whitespace or formatting. |
| `chain_entry` | The receipt event's audit `sequence` and `hash`. |

Read the terminal status and verification result before drawing a conclusion. A receipt can record failure or compensation; its existence alone does not establish **Landed**. Provider request IDs and other evidence can be unavailable and are recorded accordingly.

The document is stored when issued, rather than rebuilt from current action settings at download time. Its hash and chain reference support audit inspection; they are not an external signature or independent proof of completeness.

### Why is the receipt missing or forbidden?

- **No download button:** that action has no stored decision receipt. Pending actions and older records may not have one; inspect the workspace event export instead.
- **Access denied:** use a signed-in browser session with access to the action's workspace. An MCP workspace key or Signals secret cannot substitute for the browser session.
- **Receipt not found:** confirm the workspace and action. A receipt from another workspace or a missing receipt cannot be downloaded through this action's link.

## Integrity versions

The JSON export retains the hash and predecessor fields. The current Audit page does not display an integrity verdict or recomputation panel; downloading the file is not itself a verification of the chain.

| Segment | Meaning |
| --- | --- |
| Historical v1 | Preserves predecessor continuity, but its hash cannot be recomputed completely from durable row fields. |
| Checkpoint | Bridges the preserved v1 tail into the v2 segment. |
| v2 | Uses a durable canonical representation so stored row hashes can be recomputed. |

<Warning>
  The hash chain has no external tail anchor. Even successful recomputation of a snapshot cannot independently prove that no tail events were deleted outside that snapshot.
</Warning>

## Events to follow

| Stage | Representative events | Meaning |
| --- | --- | --- |
| Drive ownership | `folder.claim`, `folder.verification_failed`, `folder.verified` | A workspace owner claimed a Drive folder, ownership verification failed, or ownership was verified before inventory sync. |
| Policy | `policy.updated` | A workspace owner changed action-policy settings. The event records the complete before-and-after policy and is not tied to a batch or action. |
| Token lifecycle | `token.issued`, `token.revoked` | A scoped workspace key was issued or revoked, including historical token rotations. The event records durable token metadata but never the plaintext credential. |
| Proposal | `batch.proposed`, `batch.blocked` | An agent submitted a batch and policy accepted it for review or blocked it. |
| Decision | `batch.recommendation_approved`, `batch.approved`, `batch.rejected` | A person recorded a suggest-only approval, authorized execution, or rejected the proposal. |
| Execution gate | `execution.started`, `execution.blocked` | The worker began or the fresh execution-time policy check denied the batch. |
| Provider evidence | `action.provider_read_started`, `action.provider_read_observed`, `action.provider_read_classified` | A receipt-addressed read was authorized, captured, and mechanically classified. |
| Verification | `action.verified`, `execution.verified` | The exact provider object matched; all actions are Landed only after the batch-level verified event. |
| Async verification | `action.verification_handed_off`, `action.async_verification_*` | A committed ad copy remains Not Landed while scheduled verification continues. |
| Decision receipt | `action.decision_receipt_issued` | A terminal action decision document was stored and linked to the audit chain. Read its status; a receipt is not automatically a successful outcome. |
| Outcome | `outcome.checked`, `outcome.anomaly_detected` | A later provider outcome was recorded and classified. |
| Restoration | `action.rolled_back`, `batch.rolled_back`, `batch.rollback_incomplete` | Compensation restored provider state, or incomplete recovery needs attention. |

Measurement-only events explicitly say **NOT LANDED**. Do not count them as production execution acceptance.

## Investigate unexpected execution

<Steps>
  <Step title="Confirm the principal and scope">
    In the JSON export, find `batch.proposed`. Confirm the agent, account, evidence provenance, target-selection boundary, and execution-mode snapshot.
  </Step>
  <Step title="Trace both policy decisions">
    Read the proposal-time result and, for executable work, the execution-time result recorded before the provider call.
  </Step>
  <Step title="Confirm the human decision">
    Find the approval or rejection event and confirm the named person and time.
  </Step>
  <Step title="Follow the receipt evidence">
    Trace execution, raw provider observations, classifications, and terminal verification. An awaiting-verification event is not Landed.
  </Step>
  <Step title="Confirm restoration when needed">
    For failed work, find the compensation and provider-read proof. Escalate any `rollback_incomplete` event.
  </Step>
  <Step title="Revoke access if necessary">
    Revoke the Plainrouter agent connection or workspace token. Confirm the intended credential or grant is revoked. Revocation does not undo earlier provider actions.
  </Step>
</Steps>

## What happens to history after account deletion?

Deleting an eligible login account does not erase retained Actions evidence. Approval, audit, batch, and receipt records remain; where they reference the person, Plainrouter retains a disabled user record labeled **Deleted user**. Historical snapshots are preserved rather than rewritten, so an older export can still contain the actor details captured at the time.

The deleted identity cannot sign in or continue using its credentials. Registering again with the same email creates a new identity and does not restore the old access. Account deletion can still be refused when the person owns a team whose workspaces hold retained Actions records. Do not treat deleting a login as a way to delete workspace evidence or undo provider changes.
