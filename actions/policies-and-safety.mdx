title: "Agent rules and execution safety"
description: "Choose Ask, Auto or Full for agent proposals, configure action permissions, and understand approval, budget and provider-verification boundaries."
---

Open **Settings → Agent rules** to choose how agents may act in the selected workspace. **Ask** waits for approval, **Auto** permits the actions you turn on, and **Full** permits admitted agent actions without a separate person approval for each change. Every mode keeps policy, authorization and provider-verification checks.

Changing these settings requires current permission to update the workspace. Members with view access can inspect them. A Workspace key cannot change the workspace's agent mode. A listed permission does not enable an unavailable product operation.

## Execution mode

| Mode | Agent proposals |
| --- | --- |
| **Ask** (`ask`) | Every admitted change waits for a person to approve it in Inbox. |
| **Auto** (`auto`) | Only action types enabled under **What agents can do on their own** can proceed without individual approval. Other admitted changes wait for a person. |
| **Full** (`full`) | Admitted agent changes can proceed without individual approval, including supported budget raises and campaign/ad-set activation. Explicit policy blocks still prevent execution. |

Some public and agent copy calls the permission-based mode **Custom**. The current **Agent rules** selector labels it **Auto**, and API fields still use `auto`. These names describe the same permission-based mode; they do not add another execution mode.

New workspaces default to Ask. Select a mode and choose **Save**. Auto's switches cover pauses, uploads, paused ad creation, activation, campaign/ad-set creation, budget changes and automation permissions. Every required permission in a mixed batch must allow the action before that batch can run unattended.

The agent-mode decision does not expand the key's workspace, Meta ad account, scopes or grant. It does not make an unsupported action available. Older `suggest_only`, `auto_with_limits` and `full_auto` values belong to historical batch snapshots; they are not additional current choices.

## Which changes still need a person in Full?

Full no longer applies the former blanket person-approval rule to agent budget increases, campaign/ad-set resumes or creation permissions. Use Ask when you want every agent proposal to wait. Use Auto when you want to allow only selected action types without individual approval.

Full still cannot approve a refused change, widen a credential or manufacture missing provider evidence. Human decisions and system-generated account rules have their own authorization paths; the agent permission switches do not replace those checks. [Read a batch's actual policy result](/actions/review-proposals) before representing it as approved or executed.

## How are unattended budget changes limited?

In Auto, enabled agent budget raises remain subject to the configured agent budget limits. A large raise, unavailable budget/currency evidence or unverifiable recent raises can require person approval. If a limit is exceeded when execution rechecks the queued work, the write can be blocked; inspect the reason and propose the intended change again for review. Full does not use the Auto-specific multiplier hold.

### What happens when an agent turns on a new campaign or ad set?

In Auto, the enabled launch-budget safeguard also checks the first activation of a campaign or ad set created paused by Plainrouter. It compares the budget that would start spending with a comparable running budget. A large first launch, missing comparable budget or uncertain currency/state can require a person to approve it. A change that exceeds the limit at execution can be blocked and needs a new proposal for review.

This is separate from approving the paused creation. Creating an object does not authorize turning it on. Full does not use this Auto-specific approval hold. The current Agent rules page does not expose an editor for these budget-limit values; do not infer a setup control from a stored policy field.

## Why is a change blocked by workspace pause?

`workspace_paused` means the workspace is paused for forward ad changes. The proposal can be saved as blocked; switching to Full or repeating approval does not bypass the pause. `workspace_pause_state_unavailable` means the pause state could not be established. `workspace_pause_requires_review` means the batch predates a pause and needs fresh review after resumption.

Pausing turns off mutating automations and enabled account rules. Resuming the workspace does not turn them back on, reauthorize old batches or undo provider changes already made. Inspect each stored status and receipt before proposing remaining work. These response semantics do not imply that this page has a customer pause-switch control.

## Two policy gates

Proposal-time admission checks the requested actions, scope, evidence, permissions and selected mode. Execution rechecks current authorization and authoritative provider state before a write. A proposal or earlier preview is not an execution reservation.

The proposal keeps its recorded `execution_mode_snapshot`; changing current settings does not rewrite that history. Read the snapshot together with current policy and the batch's actual decision. Revoked access, unavailable critical state and other blocking results remain blocks in every mode.

An execution stop can prevent further writes. It does not undo a change already sent or verified. Use [Inbox and receipts](/actions/review-proposals) to determine what actually happened.

## What if the approver loses permission before execution?

Before the first Meta write for an approved batch, Plainrouter rechecks the approving person's current permission. If the person was removed, downgraded or is otherwise no longer authorized to approve, the batch is blocked with `approver_permission_revoked` and nothing is sent to Meta. Ask an authorized person to propose and approve the intended change again. For a Launch plan, copy it to a new draft, validate and submit it.

This check does not undo provider work that already started. Inspect the existing [receipt and batch status](/actions/review-proposals#why-was-an-approved-batch-blocked) before proposing remaining work; an old approval is not proof of current authority.

## Outcome safety

### Stored outcome check delay

Stored proposals can carry a delay before checking a verified creative action's provider outcome. The accepted range is 1–168 hours. Resume and daily-budget changes use a separate window of three complete account-local days after the provider-write day, with the first check scheduled one hour after that window ends. See [outcome windows and prerequisites](/actions/review-proposals#how-are-later-performance-outcomes-checked).

### Stored loss threshold

The stored percentage classifies a measurable management outcome as `held` or `lost`. The accepted range is 1–999.99%; the API retains the field name `anomaly_threshold_percent`. Inbox records the threshold used with the comparison.

The comparison uses eligible counted arrivals and retained Meta spend, not purchase CPA or aggregate Signals reconciliation. A `lost` verdict can create a separate [inverse proposal](/actions/review-proposals#does-a-lost-outcome-create-an-inverse-proposal), with current-state checks and Ask/Full approval behavior. It does not directly compensate the original action. Check the recorded proposal before submitting another change; neither verdict guarantees future performance.

## What happened to the older policy controls?

The current Agent rules page focuses on mode and agent permissions. The former Account rules and outcome-setting sections are no longer shown below that card. Existing [account-rule APIs](/actions/account-rules), recorded policy parameters, outcome checks and audit history remain separate contracts; do not infer that an older API field is an editable control on this page.

## Execution boundaries

A supported MCP proposal writes a Plainrouter proposal and can read provider state; it does not itself perform the final Meta mutation. Created ad copies remain paused until a separate admitted activation action. Video upload execution remains unavailable. New requests refuse retired action types even when an older SDK enum contains them. [Supported actions and refusals](/actions/overview#supported-action-types).

Landed still requires a durable provider receipt and exact verification for every action in the batch. Full mode, an approval or a successful write response alone does not establish Landed or a performance improvement.
