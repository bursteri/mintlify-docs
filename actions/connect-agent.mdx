PlainRouter exposes a remote Model Context Protocol server at:

```text
https://plainrouter.com/mcp
```

PlainRouter supports interactive OAuth and owner-issued workspace tokens. Both methods bind the client to one workspace, one Meta ad account, and an explicit permission set.

This page covers OAuth. PlainRouter publishes OAuth discovery metadata, so compatible clients can start authorization automatically. If your client uses a fixed bearer credential instead, [issue a workspace token](/actions/workspace-tokens).

## Before you begin

You need:

- A PlainRouter account with access to the intended workspace.
- An active Meta ad account connection.
- An MCP-compatible client with remote HTTP and OAuth support. For a client without OAuth support, use a [workspace token](/actions/workspace-tokens).
- A clear choice of the one advertising account the client should use.

For creative-library reads, the Meta connection needs `ads_read` or `ads_management`. Governed creative execution needs `ads_management`.

## Authorize with OAuth

<Steps>
  <Step title="Add the PlainRouter MCP server">
    In your MCP client, add a remote server using `https://plainrouter.com/mcp`.
  </Step>
  <Step title="Start OAuth authorization">
    Follow the sign-in or authorization prompt opened by the client. Sign in to PlainRouter if needed.
  </Step>
  <Step title="Review permissions">
    Choose the read, proposal, and creative permissions the client needs. Avoid granting creative write access to a client that only analyzes Signals.
  </Step>
  <Step title="Choose the advertising account">
    Select the exact account for this connection. The resulting agent principal is bound to that account.
  </Step>
  <Step title="Return to your client">
    Finish the redirect or device authorization flow. The client can now initialize the PlainRouter MCP server.
  </Step>
</Steps>

## Permissions

| Permission | Allows |
| --- | --- |
| `ad-account.read` | Read the approved account and its PlainRouter Signals context. |
| `signals.verify` | Write the identity-free, consent-safe Signal verification event used for onboarding. |
| `actions.propose` | Submit actions through workspace policy and the approval pipeline. |
| `creative.read` | Read the approved Meta account's creative library. |
| `creative.write` | Stage creative assets and propose creative changes. It does not bypass `actions.propose`. |

The agent cannot supply another account ID to widen access. Creative tools recheck that provider objects belong to the approved account.

<Warning>
  Creative write permission is not direct mutation authority. `upload-asset` and `duplicate-ad-with-creative` return a governed proposal. A later policy decision or human approval determines whether execution is queued.
</Warning>

## Recommended workflows

For Signals analysis:

1. `get_account_state`
2. `verify_signal_ingestion` if Signal activation is still waiting for its server-side check
3. `get_signal_health`
4. `get_performance` when stored reconciliation is relevant
5. `propose-actions` only after the evidence and human-supplied target are clear

For a creative variant:

1. `get_account_state`
2. `get-creative-library`
3. `upload-asset` if the approved account does not already contain the intended image
4. `duplicate-ad-with-creative` using an asset ID returned by a PlainRouter tool
5. Direct the person to the returned `approval_queue_url`

Ask the agent to state clearly whether a proposal is suggest-only, pending approval, blocked, awaiting verification, or Landed.

## Authorization lifetime and revocation

PlainRouter issues short-lived access tokens and refreshable authorization. The person who created an agent connection can revoke it in PlainRouter. Revocation disables the principal and its OAuth tokens.

Reconnect if the selected account changes or the underlying Meta permissions change. One OAuth client can create separate, isolated connections for different users or accounts.

Workspace tokens use an explicit expiry and owner-managed rotation instead. See [Workspace tokens](/actions/workspace-tokens) for their lifecycle.

## Troubleshoot

### The client receives `401 Unauthorized`

Confirm the client followed the OAuth metadata advertised by the MCP endpoint. Remove a stale connection and authorize again if its tokens were revoked or expired without a usable refresh token.

For a workspace token, confirm that the client sends the complete token as a bearer credential and that the token has not expired or been revoked.

### A creative tool reports a missing permission

Reauthorize the PlainRouter connection with `creative.read` for library access or both `creative.write` and `actions.propose` for proposal-producing creative tools.

### PlainRouter asks you to reconnect Meta

The selected account may lack an active Meta connection or the required `ads_read` or `ads_management` access. Reconnect Meta, confirm the same ad account, and retry the same idempotent request.

### The wrong account appears

Revoke the connection and authorize it again with the correct advertising account. Tool calls do not accept an account override.

### Signals tools show setup required

The account may be authorized correctly while its workspace has no active Signal or destination. Complete [Signals setup](/signals/overview) and call the tools again.
